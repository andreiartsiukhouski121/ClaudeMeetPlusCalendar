# Тест-план и структура регрессионного сьюта: логин + главная страница

Документ фиксирует **организацию тестов** и **полный перечень кейсов** для двух фич:

- **Фича 1** — страница логина `/auth/login`;
- **Фича 2** — главная страница `/` (дашборд встреч).

Код тестов здесь не приводится — только структура, конвенции, кейсы и команды.

### 1.2 Где живёт регрессионный сьют

`e2e/regression/<feature-slug>/` — один каталог на фичу, `feature-slug` в kebab-case (`auth-login`, `home-dashboard`).

Почему так, а не `e2e/api/` + `e2e/web/`:

- Требование — **разбиение по фичам**, а не по типу теста. Правя фичу, разработчик открывает **один каталог** и видит там всё: API-кейсы, функциональные кейсы, описание UT и парные спеки.
- Деление по типу теста сохраняется, но переезжает **в имя файла** — суффикс `.api.` / `.functional.`. Тип теста — атрибут файла, а не его места в дереве.
- `e2e/smoke/` отделён от `e2e/regression/`: смоук — это «инфраструктура жива» (сервер поднялся, сид на месте), он не привязан к фиче и должен падать первым и понятно.

### 1.3 Имена парных файлов

| Роль                                                      | Шаблон имени                    | Пример                           |
| --------------------------------------------------------- | ------------------------------- | -------------------------------- |
| Человекочитаемые кейсы, API-контракт                      | `<feature>.api.cases.md`        | `auth-login.api.cases.md`        |
| Исполняемый спек, API-контракт (Playwright, проект `api`) | `<feature>.api.spec.ts`         | `auth-login.api.spec.ts`         |
| Человекочитаемые кейсы, UI                                | `<feature>.functional.cases.md` | `auth-login.functional.cases.md` |
| Исполняемый спек, UI (Playwright, проект `web`)           | `<feature>.functional.spec.ts`  | `auth-login.functional.spec.ts`  |
| Кейсы юнит-тестов фичи                                    | `<feature>.unit.cases.md`       | `auth-login.unit.cases.md`       |

Обоснование:

- **Одинаковая база имени + разный суффикс** — прямая реализация требования «называть и организовывать одинаково». Парность видна одним `ls` каталога фичи.
- **`.cases.md` vs `.spec.ts`** — расширение однозначно отделяет описание от кода, а `cases` читается как «набор тест-кейсов» и не путается с `README`.
- **`functional`, а не `web`/`ui`/`e2e`** — так сформулировано требование («API-тесты и функциональные тесты»). Ровно два типа файлов на фичу.
- **Суффикс = маршрутизация в проект Playwright.** Имя файла — единственный источник истины о том, какой проект (и, значит, какой `baseURL` и нужен ли браузер) исполняет тест. Это исключает класс ошибок «положил браузерный тест в API-каталог и получил `page.goto` на :3101».

Жёсткое правило: **спек без парного `.cases.md` и `.cases.md` без парного спека — блокер.** Проверяется автоматически (1.6).

### 1.4 Точный диф `playwright.config.ts`

Сейчас проекты разделены по `testDir`. После переезда файлы одной фичи лежат в одном каталоге, поэтому маршрутизация переходит на `testMatch` по суффиксу.

```diff
   // baseURL задаётся только на уровне проекта, иначе api унаследует адрес web.
   projects: [
-    { name: 'api', testDir: './e2e/api', use: { baseURL: API_URL } },
-    { name: 'web', testDir: './e2e/web', use: { ...devices['Desktop Chrome'], baseURL: WEB_URL } },
+    // Файлы разложены по фичам (e2e/regression/<feature>/), поэтому проект выбирается
+    // не каталогом, а суффиксом имени файла:
+    //   *.api.spec.ts        -> проект api  (фикстура request, baseURL :3101, браузер не нужен)
+    //   *.functional.spec.ts -> проект web  (Desktop Chrome, baseURL :3100)
+    // Дефолтный testMatch ловит любой *.spec.ts, поэтому его надо переопределить в обоих
+    // проектах: иначе браузерный спек уедет в api и получит page.goto на :3101.
+    // Файл без одного из двух суффиксов не попадёт НИ в один проект и молча не запустится —
+    // от этого страхует e2e/suite-integrity.api.spec.ts.
+    { name: 'api', testMatch: /.*\.api\.spec\.ts$/, use: { baseURL: API_URL } },
+    {
+      name: 'web',
+      testMatch: /.*\.functional\.spec\.ts$/,
+      use: { ...devices['Desktop Chrome'], baseURL: WEB_URL },
+    },
   ],
```

Не меняется: `testDir: './e2e'` на верхнем уровне (проекты его наследуют); `fullyParallel: true` (гонки решаются данными и локальным `serial`, см. 5.4); порты 3100/3101, `webServer`, таймауты — трогать запрещено (`CLAUDE.md`).

Корневой `tsconfig.json` изменений не требует: `include` уже включает `e2e/**/*.ts`, `types: ["node"]`
— мета-тест использует `node:fs`.

`eslint.config.mjs` **правится обязательно** (`T0.6`). Блок `files: ['e2e/**/*.ts']` покрывает новые
пути уже сейчас, но в `eslint-plugin-playwright` пресете `flat/recommended` три правила стоят в
`warn`, а ESLint с предупреждениями выходит с кодом `0` — то есть `waitForTimeout` и `test.skip`
проходят шаг 2 пайплайна зелёными, хотя §6.3 называет их блокерами (проверено чтением пресета):

```diff
   {
     ...playwright.configs['flat/recommended'],
     files: ['e2e/**/*.ts'],
+    // flat/recommended держит эти четыре в warn, а ESLint с warn выходит с кодом 0.
+    // §6.3 считает их блокерами — значит error.
+    rules: {
+      ...playwright.configs['flat/recommended'].rules,
+      'playwright/no-wait-for-timeout': 'error',
+      'playwright/no-skipped-test': 'error',
+      'playwright/no-conditional-in-test': 'error',
+      'playwright/no-page-pause': 'error',
+    },
   },
```

Вариант `eslint . --max-warnings=0` в корневом скрипте `lint` отвергнут: он делает блокером **любое**
предупреждение во всём репозитории, включая правила, к устойчивости тестов не относящиеся, и
поднимает цену любой будущей настройки линта. Поднимаем в `error` ровно те три правила, которые §6.3
объявляет блокерами.

`test.fixme` из §6.5 при этом остаётся разрешённым: `no-skipped-test` в `eslint-plugin-playwright@2.11`
реагирует на `test.skip`/`describe.skip` и не знает про `fixme` (проверено — строки `fixme` в сборке
плагина нет). То есть механизм «нашли дефект → `test.fixme` со ссылкой на задачу» не конфликтует с
правкой.

### 1.6 Парность файлов и мета-тест конвенции

`e2e/suite-integrity.api.spec.ts` (проект `api`, браузер не нужен, работает через `node:fs`) — исполняемая версия конвенции:

1. каждый `e2e/**/*.spec.ts` заканчивается на `.api.spec.ts` или `.functional.spec.ts` (иначе файл не попадёт ни в один проект и молча не запустится);
2. у каждого спека есть парный `.cases.md` с тем же базовым именем в том же каталоге;
3. у каждого `.cases.md` есть парный спек — кроме `*.unit.cases.md`;
4. для каждого `*.unit.cases.md` все упомянутые в нём пути к спекам в `apps/**` существуют на диске;
5. каждый ID кейса из `.cases.md` встречается в тексте парного спека — кроме `*.unit.cases.md`, у которых парного спека нет по правилу 3 и двусторонность обеспечивают правила 7 и 8. Кейс, сознательно не автоматизированный, помечается в `.cases.md` строкой `- **Не автоматизирован:** <причина + ссылка на задачу>` — мета-тест распознаёт **только** этот синтаксис и такой ID в спеке не требует;
6. ни один `.cases.md` не содержит дублирующихся ID;
7. для каждого `*.unit.cases.md` каждый ID кейса встречается в тексте **того** спека, под чьим
   заголовком он перечислен (иначе ID юнит-кейсов живут только в markdown: ни отфильтровать, ни
   проверить, что кейс вообще автоматизирован, нельзя);
8. каждый `apps/**/src/**/*.spec.ts` упомянут хотя бы в одном `*.unit.cases.md` (правила 4 и 7
   односторонние: без правила 8 новый юнит-спек может не попасть в документацию, и это никто не
   заметит). Исключение — тоже явным списком: `UNIT_SPEC_EXEMPT = ['apps/api/src/app.controller.spec.ts']`,
   единственный baseline-спек скаффолда, не относящийся ни к одной из двух фич. Новые спеки в этот
   список не добавляются: попал спек в `apps/**/src/**` — попал и в `*.unit.cases.md`.

**Правила 1–3 не применяются к самому `e2e/suite-integrity.api.spec.ts`** — он не описывает фичу, а
исполняет конвенцию, поэтому парного `suite-integrity.api.cases.md` у него нет и быть не должно.
Исключение задаётся явным списком в коде мета-теста, **не** regexp'ом:

```ts
const SELF_EXEMPT = ['suite-integrity.api.spec.ts'];
```

Явный список — потому что regexp вида «файлы в корне `e2e/`» со временем начнёт покрывать
что-то ещё, и первый же спек, положенный в корень «на минутку», выпадет из проверки парности молча.
Без этого исключения шаг 1 пайплайна (§6.2) краснеет на собственном файле — а это шаг, который
блокирует все последующие.

Ревью такое не ловит, а мета-тест ловит на `pnpm e2e`.

### 1.7 Распространяется ли парность на юнит-тесты

**Частично, и осознанно.** Юнит-спек остаётся рядом с кодом (`apps/api/src/auth/auth.service.spec.ts`), markdown на каждый юнит-спек **не создаётся**. Вместо этого — один `<feature>.unit.cases.md` на фичу, где кейсы сгруппированы по спек-файлам и каждая группа начинается со строки-ссылки на путь спека.

Почему так:

- Юнит-тест тестирует **функцию, а не пользовательский сценарий**. Его «шаги» — это «вызвать `login(dto)`»; описывать это прозой — дублирование кода на русском, устаревающее в первый же рефакторинг.
- Юнит-спеки меняются вместе с кодом, в одном коммите, и живут в другом пакете. Зеркальное дерево markdown в `e2e/` неизбежно рассинхронизируется — а рассинхронизированная документация хуже её отсутствия.
- Требование «карта фичи в одном месте» при этом выполняется: открыв `e2e/regression/auth-login/`, видно все уровни проверок фичи, включая юниты и точные пути к ним. Существование путей проверяет мета-тест (1.6, пункт 4), обратную сторону — что ни один спек не забыт в документации, а ни один ID не остался неавтоматизированным — правила 7 и 8 того же мета-теста.

Формально: **парность `cases.md` ↔ `spec.ts` обязательна для регрессионного сьюта; для юнитов действует парность `unit.cases.md` ↔ перечень путей спеков, проверяемая автоматически.**

**Отступление от буквы требования — названо явно.** Пользователь просил парность «файл кейсов ↔ файл
кода» для всех типов проверок. Читаем это так: требование «на каждую фичу два файла тестов — API и
функциональные» сформулировано **для регрессионного сьюта**, а юнит-тесты запрошены отдельным
требованием («обязательный запуск UT»), без указания на зеркальное дерево markdown. Поэтому для
юнитов парность реализуется как «один `<feature>.unit.cases.md` ↔ перечень путей спеков», а
компенсируют её правила 4, 7 и 8 §1.6: пути обязаны существовать, каждый ID обязан встречаться в
тексте именно того спека, под которым он перечислен, и каждый спек в `apps/**` обязан быть упомянут
в документации. Проверка двусторонняя, а не декоративная.

**Альтернатива, если заказчик потребует буквального прочтения** — вариант Б:
`e2e/regression/<feature>/unit/<basename>.unit.cases.md` на каждый спек, где `<basename>` совпадает с
именем спека (`auth.service.unit.cases.md` ↔ `apps/api/src/auth/auth.service.spec.ts`). Цена — 9
дополнительных markdown-файлов на две фичи и 9 точек рассинхрона; правило 3 §1.6 придётся расширить,
а правило 8 — переписать на попарное сопоставление. Переход на вариант Б не меняет ни один ID кейса и
ни один спек, поэтому его можно выполнить отдельной задачей в любой момент.

### 1.9 Теги и запуск по одной фиче

Теги задаются опцией `tag` у `test.describe` (нативный механизм Playwright, работает с `--grep`), а не текстом в заголовке — заголовок остаётся человекочитаемым:

- `@regression` — все кейсы регрессионного сьюта;
- `@smoke` — `e2e/smoke/**`;
- `@auth-login`, `@home-dashboard` — фича;
- `@mutating` — кейс изменяет данные (`POST /meetings`), нужен для `--grep-invert`;
- `@p0` — критичный минимум для быстрой проверки перед пушем.

```bash
pnpm e2e                                              # всё
pnpm e2e --grep @auth-login                           # одна фича целиком (API + UI)
pnpm e2e --grep @home-dashboard
pnpm e2e --project=api --grep @auth-login             # только контракт API (без браузера)
pnpm e2e --project=web --grep @auth-login            # только UI
pnpm e2e e2e/regression/auth-login                   # по пути, без зависимости от тегов
pnpm e2e e2e/regression/home-dashboard/home-dashboard.api.spec.ts   # один файл
pnpm e2e --grep "HD-FN-07"                            # один кейс по ID
pnpm e2e --grep "@p0"                                 # только критичное
pnpm e2e --grep-invert @mutating                      # диагностика флака
pnpm e2e e2e/suite-integrity.api.spec.ts              # мета-проверка конвенции
pnpm e2e:report                                       # отчёт после падения

pnpm test                                             # все юниты обеих фич
pnpm test:auth-login                                  # юниты одной фичи
pnpm test:home-dashboard
```

Скрипты в корневой `package.json` (добавить к существующим, ничего не переименовывая):

```json
"e2e:smoke": "playwright test e2e/smoke",
"e2e:regression": "playwright test e2e/regression",
"e2e:auth-login": "playwright test --grep @auth-login",
"e2e:home-dashboard": "playwright test --grep @home-dashboard",
"e2e:p0": "playwright test --grep @p0",
"test:auth-login": "pnpm -r test -t \"AL-UT-\"",
"test:home-dashboard": "pnpm -r test -t \"HD-UT-\""
```

`test:<feature>` обязательны, а не «удобны»: требование пользователя — «проверки запускаются по
каждой фиче в изоляции». Для e2e изоляция есть (`--grep @auth-login`), а `pnpm test` без фильтра
гоняет юниты **обеих** фич сразу, то есть изоляции для UT нет вовсе. `-t` у `vitest run` фильтрует по
имени теста, поэтому фильтр работает только вместе с правилом «заголовок юнит-теста начинается с ID
кейса» (§2).

**Двойное `--` в этих скриптах запрещено.** `pnpm -r test -- -t "AL-UT-"` прокидывает в скрипт пакета
**литеральный** `--`, после которого `vitest` перестаёт считать `-t` опцией и гоняет все тесты —
изоляции по фиче нет, а `pnpm test:auth-login` вернёт число полного прогона (проверено пробой в ревью
2, NB1). Правильная форма — без `--`: `pnpm -r test -t "AL-UT-" --passWithNoTests`. Побочный эффект
`--`: охват меняется на `all 5 workspace projects`, и корневой пакет рекурсивно вызывает сам себя.

`--passWithNoTests` в этих скриптах нужен для пакета, в котором **вообще нет** spec-файлов
(`apps/web` до `T1.4`): такой `vitest run` пишет `No test files found` и выходит с кодом 1. Фильтр
`-t` без совпадений сам по себе безопасен — тесты помечаются `skipped`, код 0 (проверено). Флаг
приписан к корневым `test:<feature>`, чтобы не трогать `test` в пакетах.

В `apps/web/package.json` добавить `"test": "vitest run --passWithNoTests"` — иначе корневой
`pnpm test` (`pnpm -r test`) не увидит веб-юниты. Флаг здесь тоже обязателен и это валидная опция
`vitest run` (проверено `vitest run --help`): на момент `T0.3` спеков в web ещё нет, а `vitest run`
без тестов выходит с кодом 1 и роняет корневой `pnpm test`, то есть DoD `T0.3` без флага
невыполним.

## 2. Шаблон файла тест-кейсов

Каждый `*.cases.md` имеет фиксированную структуру:

- шапка: путь парного спека, проект Playwright, теги, команда запуска, общие предусловия;
- таблица-сводка: ID, заголовок, приоритет, тег, имя теста в спеке;
- раздел «Кейсы» — по одному подразделу на кейс с полями: приоритет, тип, теги, предусловия, нумерованные шаги, ожидаемый результат, имя теста в спеке.

Правила ID: `<ФИЧА>-<ТИП>-<NN>`, где ФИЧА = `AL` (auth-login), `HD` (home-dashboard), `SM` (smoke); ТИП = `API` | `FN` (functional) | `UT` (unit); `NN` — двузначный, **не переиспользуется** после удаления кейса.

**Заголовок теста в спеке обязан начинаться с ID.** Это даёт `pnpm e2e --grep "HD-FN-07"`, читаемый отчёт и автоматическую проверку парности (1.6, пункт 5).

**Заголовок юнит-теста тоже обязан начинаться с ID кейса** — `it('AL-UT-09 — hash не равен plain', …)`.
Без этого ID `AL-UT-*`/`HD-UT-*` существуют только в markdown: нельзя ни запустить юниты одной фичи
(`pnpm test:auth-login` фильтрует `vitest` по имени теста, §1.9), ни проверить правилом 7 §1.6, что
описанный кейс вообще автоматизирован.

### Готовый пример одного кейса

```markdown
### AL-FN-03 — неверный пароль: видимая ошибка, пользователь остаётся на странице логина

- **Приоритет:** P0
- **Тип:** UI-функциональный
- **Теги:** `@p0`
- **Предусловия:**
  - Пользователь `teacher@purpleschool.test` существует в сиде.
  - Браузерный контекст чистый (без cookie сессии): `test.use({ storageState: undefined })`.
    Уточнение: `page` и так чистый — глобального `storageState` в `playwright.config.ts` нет, и
    сессию тест наследует только если явно берёт фикстуру `authedPage`. Конструкция оставлена как
    защита от будущего добавления глобального состояния в конфиг; другой роли у неё нет, и
    рассчитывать на неё как на «сброс сессии» нельзя.
- **Шаги:**
  1. Открыть `/auth/login`.
  2. В поле «Email» ввести `teacher@purpleschool.test`.
  3. В поле «Пароль» ввести `wrong-password`.
  4. Нажать кнопку «Войти».
- **Ожидаемый результат:**
  - Виден элемент с ролью `alert`, содержащий текст об ошибке входа.
  - URL остаётся `/auth/login` (редиректа на `/` не произошло).
  - Приветствие с email на странице отсутствует.
  - Cookie сессии в контексте не появилась.
  - Текст ошибки не содержит служебных деталей (стектрейса, слова `passwordHash`).
- **Имя теста в спеке:** `AL-FN-03 — неверный пароль: видимая ошибка, пользователь остаётся на странице логина`
```

## 5. Правила устойчивости тестов

Основано на `.claude/skills/playwright-verify/SKILL.md`, раздел 4.

### 5.1 Локаторы

- Разрешено: `getByRole`, `getByLabel`, `getByText`, `getByPlaceholder`; `getByTestId` — только когда роли объективно не хватает (например, счётчик встреч без собственной роли).
- **Запрещены CSS-цепочки и селекторы по классам.** В `apps/web` — CSS-модули с хешированными именами: такой локатор умирает на следующем билде.
- Поля формы адресуются через `getByLabel('Email')` / `getByLabel('Пароль')` — это заодно проверяет, что у полей есть связанные `label` (требование доступности).
- Кнопки — `getByRole('button', { name: 'Войти' })` с точным именем из спецификации фичи.
- Список встреч — `getByRole('list')` + `getByRole('listitem')`. Отсюда требование к разметке: список должен быть `ul`/`li`, а не набор `div`.
- Сообщение об ошибке логина — `getByRole('alert')`. Отсюда требование: контейнер ошибки имеет `role="alert"`.

### 5.2 Ожидания

- Только web-first assertions: `await expect(locator).toBeVisible()`, `toHaveText`, `toHaveCount`, `await expect(page).toHaveURL(...)`. Они сами ждут до `expect.timeout` (10 с в конфиге).
- **`waitForTimeout` запрещён** без исключений.
- **`await` перед `expect(...)`** обязателен для асинхронных матчеров: type-aware линта в репозитории нет, забытый `await` проходит и линт, и тест — зелёный тест, не проверивший ничего. Синтаксически это ловит `eslint-plugin-playwright` на `e2e/**/*.ts`, но ревьюер проверяет глазами тоже.
- `test.only` не коммитить (`forbidOnly` в CI).
- Смену URL после Server Action ждать через `await expect(page).toHaveURL('/')`, а не `waitForNavigation`.

### 5.3 Консоль

`e2e/fixtures/console.ts` экспортирует хелпер, который подписывается на `console` и `pageerror`, отбрасывает шум dev-сервера по списку паттернов (HMR-эндпоинт `/_next/hmr`, `WebSocket connection to`, сообщения React DevTools) и возвращает массив проблем. Кейсы `AL-FN-08` и `HD-FN-10` используют его; собственные регулярки в спеках не дублируются. Подписка ставится **до** `page.goto`, иначе ранние ошибки теряются.

### 5.4 Гонки при `fullyParallel: true`

Проблема: `POST /meetings` меняет общее состояние сервера, поднятого один раз на весь прогон; проекты `api` и `web` идут параллельно и могут задеть одни данные.

Рассмотренные варианты:

| Вариант                                              | Оценка                                                                                                                                                               |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Полный `fullyParallel: false`                        | Отвергнут: прогон замедляется на всём сьюте, включая 48 read-only кейсов, из-за 5 мутирующих (`HD-API-13`, `HD-API-17`, `HD-API-20`, `HD-FN-07`, `HD-FN-08`).        |
| Сброс состояния между тестами                        | Отвергнут: серверы общие и поднимаются один раз, «сброс» требует эндпоинта очистки и глобального лока; появляется тестовый чёрный ход в продовом API и точка отказа. |
| Только `test.describe.configure({ mode: 'serial' })` | Недостаточно: сериализует тесты внутри файла, но не между проектами `api` и `web`, которые идут одновременно.                                                        |

**Выбранное решение — комбинация механизмов:**

1. **Изоляция данными (основной механизм).** Мутирующие кейсы работают под выделенными пользователями: `planner@…` — только в `*.api.spec.ts`, `organizer@…` — только в `*.functional.spec.ts`. `teacher` и `student` объявлены read-only, любая мутация под ними — блокер на ревью. Разные пользователи для разных проектов убирают межпроектную гонку без синхронизации, потому что `GET /meetings` изолирован по `userId` (это проверяется кейсами `HD-API-06`, `HD-API-17`).
2. **`test.describe.configure({ mode: 'serial' })` на мутирующем `describe` (страховка).** Внутри одного файла два `@mutating`-теста под одним пользователем могут пойти в разных воркерах — serial-блок это снимает. Мутирующие кейсы выносятся в отдельный `describe` в конце файла; остальная часть файла остаётся параллельной.
3. **Относительные ассерты на счётчики (обязательное правило).** Мутирующие кейсы никогда не проверяют абсолютное число («стало 2 встречи»): они читают `N` до действия и ждут `N + 1`. Это последняя линия защиты: даже при повторном прогоне на непочищённых данных или с retry тест останется корректным. Абсолютные числа допустимы только для read-only пользователей с гарантированным сидом.
4. **Уникальные названия создаваемых встреч** (`title` с суффиксом-таймстампом) — чтобы `toContainText` не совпал со встречей от прошлого прогона.
5. **Создаваемые встречи всегда датируются 2030 годом** (`2030-01-01T10:00` в UI, `2030-01-01T10:00:00.000Z` в API). Сортировка — `startsAt` DESC, срез — топ-3, поэтому ассерт «новая встреча первая в списке» верен только если её дата позже любой сид-встречи владельца (у `organizer` — `2026-01-14T10:00:00.000Z`, у `planner` — `2026-01-16T13:00:00.000Z`). Дата «сегодня» или `Date.now()` сделает `HD-FN-07` и `HD-API-13` зависимыми от сида и от календаря. Обязательное правило, а не рекомендация: без даты в шагах кейс вообще не выполняется — `required` на инпутах запрещён (риск 20 плана имплементации), и пустая отправка формы вернёт ошибку валидации, а не создаст встречу.

Тег `@mutating` позволяет диагностировать флак: `pnpm e2e --grep-invert @mutating` должен быть стабильно зелёным при любом состоянии данных.

### 5.5 Как логиниться в функциональных тестах

Ограничение архитектуры: сессионная cookie **httpOnly** и ставится Server Action веб-приложения; JWT из Nest браузер не видит.

**Выбранное решение: тестовая опция `authUser` + worker-scoped кэш `authStateFor` (функция
«пользователь → файл `storageState`») + test-scoped `authedPage` (новый контекст на каждый тест).**
Три сущности, а не одна:

```ts
// e2e/fixtures/auth.fixture.ts
export const test = base.extend<
  { authUser: SeedUserKey; authedPage: Page },
  { authStateFor: (user: SeedUserKey) => Promise<string> }
>({
  // worker-scoped: значение — функция, поэтому зависимости от тестовой опции нет
  authStateFor: [
    async ({ browser }, use, workerInfo) => {
      const cache = new Map<SeedUserKey, string>();
      await use(async (user) => {
        if (!cache.has(user)) cache.set(user, await uiLogin(browser, user, workerInfo));
        return cache.get(user)!;
      });
    },
    { scope: 'worker' },
  ],
  authUser: ['teacher', { option: true }], // тестовая опция — её можно менять в describe
  authedPage: async ({ browser, authStateFor, authUser }, use) => {
    /* новый context+page из файла authStateFor(authUser) */
  },
});
```

- **Почему worker-scoped кэшируется функция, а не само состояние.** Прямолинейная схема
  (`authUser` как worker-scoped опция + worker-scoped `authedState`) **не работает** — Playwright
  1.62.1 отвергает её на этапе загрузки файла: `test.use({ authUser })` в `describe` для
  worker-scoped опции даёт `Cannot use({ authUser }) in a describe group, because it forces a new
worker`, то есть падает весь спек, а не отдельный кейс. Симметричный обход тоже закрыт: сделать
  `authUser` тестовой опцией и оставить `authedState` worker-фикстурой нельзя —
  `worker fixture "authedState" cannot depend on a test fixture "authUser"`. Перенести
  `test.use({ authUser: 'organizer' })` на верхний уровень файла невозможно: в том же файле живут
  кейсы под `teacher`, а разбить файл на два — нарушить требование «на фичу 2 файла тестов».
  Поэтому worker-фикстура возвращает **функцию** получения состояния: зависимости от тестовой опции
  у неё нет, а логин под каждого пользователя всё равно выполняется один раз на воркер (проверено
  прогоном: второй тест под `teacher` переиспользует первый логин, для `organizer` выполняется
  второй). Оба запрета — рантайм-проверки Playwright, `pnpm typecheck` их не ловит: типы пару
  `{ scope: 'worker', option: true }` разрешают.
- **Почему `authedPage` — test-scoped, а не worker-scoped:** worker-scoped `page`, переиспользуемая
  несколькими тестами, ломает изоляцию — сохраняются URL предыдущего теста и накопленные подписки
  `page.on('console')`, что бьёт прямо в `HD-FN-10` («список проблем консоли пуст»). Переиспользуется
  **только состояние** (файл `storageState`), а контекст и страница создаются на каждый тест.
- **Где хранится состояние:** файл внутри `workerInfo.project.outputDir` с суффиксами
  `workerInfo.workerIndex` и имени пользователя (`WorkerInfo` даёт и `project: FullProject` c
  `outputDir`, и `workerIndex` — проверено по `playwright/types/test.d.ts`). Имя пользователя в
  суффиксе обязательно: один воркер держит состояния нескольких пользователей.
- **Почему через UI, а не подделкой cookie:** формат и подпись значения cookie — внутренняя деталь веб-слоя. Собирая cookie руками, тест дублирует прод-логику сессии и краснеет/зеленеет невпопад при её изменении. UI-логин проходит реальный путь «форма → Server Action → `POST /auth/login` → cookie» и заодно проверяет, что этот путь жив.
- **Почему один раз на воркер, а не в каждом тесте:** первый заход триггерит холодную сборку Turbopack (в конфиге под это стоит `timeout: 60_000`); полный логин перед каждым из 13 кейсов фичи 2 — это минуты на пустом месте.
- **Исключения (чистый контекст обязателен):** все кейсы фичи 1 (файл целиком), а также `HD-FN-01` и `HD-FN-11` — им нужен браузер без сессии, иначе `/auth/login` отдаст редирект на `/` и сценарий развалится. Оформляется через `test.use({ storageState: undefined })` в соответствующем `describe`. Само по себе это no-op: глобального `storageState` в `playwright.config.ts` нет, обычный `page` и так чист. Конструкция остаётся как защита от будущего добавления глобального состояния в конфиг — и как явное указание, что тест не берёт `authedPage`; другой роли у неё нет.
- **Мутирующие UI-кейсы** (`HD-FN-07`, `HD-FN-08`) идут под `organizer` (`test.use({ authUser: 'organizer' })`); `HD-FN-08` логаутится, поэтому обязан работать в **своём** контексте и не переиспользовать общий `storageState` воркера — иначе следующий тест получит разлогиненную сессию. Это отдельный контекст внутри serial-блока.
- **Токен для API-кейсов** получает `e2e/fixtures/auth.api.ts`: `POST /auth/login` через фикстуру `request`, возврат `Bearer`-строки, кэш на воркер. Браузер в проекте `api` не поднимается.
- **Эталонные данные для кейсов проекта `web`.** `e2e/fixtures/api.ts` экспортирует
  `API_BASE_URL = http://127.0.0.1:${process.env.E2E_API_PORT ?? '3101'}` (та же формула, что в
  `playwright.config.ts`) и фикстуру `apiRequest` = `request.newContext({ baseURL: API_BASE_URL })`.
  Кейсы `HD-FN-03` и `HD-FN-05`, которым нужны `total`/`items` из Nest, берут их через `apiRequest`,
  а **не** через `request`: в проекте `web` у `request` `baseURL` = `:3100`, то есть запрос ушёл бы в
  Next и кейс был бы нереализуем как написан. BFF это не нарушает: запрос идёт из Node-процесса
  теста, а не из браузера; браузерный трафик проверяет `HD-FN-11`.

### 5.6 Прочее

- Адреса только `127.0.0.1`; в спеках — относительные пути (`page.goto('/')`, `request.get('/meetings')`), `baseURL` задан на уровне проекта.
- Порты 3100/3101 не менять на 3000/3001 (`CLAUDE.md`): на 3000 может висеть `next start` со старой сборкой и дать ложное «зелено».
- Контрольный опыт на новый кейс: сломать проверяемое поведение в исходнике, убедиться, что тест краснеет, откатить. Зелёный тест на сломанной фиче хуже отсутствия теста.
- Логины/пароли/названия встреч — только из `e2e/fixtures/seed.ts`. Хардкод в спеке — блокер на ревью.

## 6. Спецификация скила-верификатора

**Имя: `regression-verify`.** Файл — `.claude/skills/regression-verify/SKILL.md`.

Почему отдельный скил, а не правка `playwright-verify`: у них разные триггеры и разная цена. `playwright-verify` — быстрая проверка одного изменения (MCP-браузер + один спек). `regression-verify` — приёмка фичи целиком: полный прогон всех уровней проверок, ревью сьюта на соответствие конвенции, отчёт. Смешивание превратит быструю проверку в десятиминутный ритуал, и её начнут пропускать.

### 6.1 Frontmatter

Поле `name` — `regression-verify`. `description` должно называть и предмет, и триггеры: приёмка фичи по регрессионному сьюту `e2e/regression`, обязательный прогон юнит-, API- и функциональных тестов, ревью парности `cases.md`/`spec.ts` и отчёт; срабатывает на «прогони регресс», «прими фичу», «проверь регрессионный сьют», «verify the regression suite», а также перед тем как отчитаться о готовности фичи.

**Про «дешёвые» шаги — без иллюзий.** Каждый запуск `pnpm e2e …` поднимает **оба** `webServer`

браузер действительно не поднимается, а Next-сервер — поднимается. Пайплайн делает пять отдельных
запусков Playwright, каждый со своим циклом старта серверов, — это цена, которую платят за
локализацию падения, а не «секунды».

### 6.3 Что считается блокером

- Любой красный тест на шагах 1–8. Заведомо красный тест в коммите — тоже блокер: если проверка
  невозможна на этом этапе, спек **не создаётся** до этапа, где он станет зелёным (так разделены
  `SM-API-02` и `SM-API-03`).
- Спек без парного `.cases.md` (или наоборот, кроме `e2e/suite-integrity.api.spec.ts` из списка
  `SELF_EXEMPT`); файл в `e2e/**` без суффикса `.api.spec.ts`/`.functional.spec.ts`.
- Юнит-спек в `apps/**/src/**`, не упомянутый ни в одном `*.unit.cases.md`; юнит-тест, чей заголовок
  не начинается с ID кейса. **Исключения:** файлы из `SELF_EXEMPT` (`suite-integrity.api.spec.ts` —
  у его тестов ID-нумерации нет по решению плана) и из `UNIT_SPEC_EXEMPT` (baseline-спек скаффолда
  `apps/api/src/app.controller.spec.ts` с заголовком `should return "Hello World!"`). Оба списка
  задаются явным перечислением в коде мета-теста, не регуляркой.
- ID кейса описан в `.cases.md`, но отсутствует в спеке и не помечен строкой
  `- **Не автоматизирован:** <причина + ссылка на задачу>` (единственный распознаваемый синтаксис, §1.6 правило 5).
- `test.only`, `test.skip` без комментария с причиной и ссылкой на задачу.
- `waitForTimeout`, ожидание с фиксированной паузой, CSS-локаторы и селекторы по классам.
- `expect(...)` без `await` для асинхронного матчера.
- Абсолютные ассерты на счётчики в `@mutating`-кейсах; мутация данных под `teacher`/`student`.
- Хардкод логина/пароля/названия встречи вместо `fixtures/seed.ts`.
- Обращение браузера к `127.0.0.1:3101` (нарушение BFF) — ловится `HD-FN-11`.
- Абсолютная дата «сегодня»/`Date.now()` у создаваемой встречи вместо 2030 года (§5.4, правило 5).
- Ненулевой список `console.error`/`pageerror` вне фильтра HMR-шума.
- Прогон на портах 3000/3001 вместо 3100/3101; правка `playwright.config.ts` в сторону 3000/3001.
- Ослабление ассерта под наблюдаемое поведение без явного объяснения в отчёте.
- Отчёт «проверено» без фактического прогона и без цифр.

### 6.4 Чек-лист код-ревью сьюта

Структура и конвенция:

- новые файлы лежат в `e2e/regression/<feature-slug>/`, имена по шаблону из раздела 1.3;
- у каждого спека есть парный `.cases.md`, и наоборот;
- `e2e/README.md` дополнен строкой фичи (кейсы, спеки, проект, команда запуска);
- теги проставлены: `@regression`, `@<feature-slug>`, `@p0`/`@mutating` где нужно;
- заголовок каждого теста начинается с ID кейса — **и в Playwright-спеках, и в юнит-спеках**, кроме
  файлов из `SELF_EXEMPT` и `UNIT_SPEC_EXEMPT` (§6.3);
- `*.unit.cases.md` ссылается на реально существующие пути спеков в `apps/**`, и наоборот: каждый
  спек в `apps/**/src/**` упомянут в документации (правила 4, 7, 8 §1.6).

Качество тестов:

- локаторы по роли/лейблу; `getByTestId` — с обоснованием в комментарии;
- все асинхронные `expect` с `await`;
- нет фиксированных пауз;
- ассерты проверяют то, что заявлено в `.cases.md`: шаги и ожидаемый результат совпадают с кодом (расхождение — блокер, потому что документация начинает лгать);
- негативные кейсы проверяют **и** статус, **и** отсутствие побочного эффекта (данные не изменились, токен не выдан);
- мутирующие кейсы: выделенный пользователь, serial-блок, относительные счётчики, уникальные `title`, `startsAt` в 2030 году;
- кейсы фичи 1, `HD-FN-01` и `HD-FN-11` работают в контексте без сессии;
- ни один кейс не полагается на порядок выполнения других кейсов;
- нет новых проверок HTTP-контракта в `apps/api/test/app.e2e-spec.ts` (по `CLAUDE.md` они идут в `e2e/`).

### 6.5 Правило «нашли проблему → отдельная задача»

Если прогон вскрыл дефект продукта или неточность в плане:

1. **План и кейсы не переписываются под наблюдаемое поведение.** Кейс отражает требование; если он красный, по умолчанию неправ код.
2. Дефект оформляется **отдельной задачей**: ID кейса, команда воспроизведения, ожидаемое vs фактическое, ссылка на трейс из `pnpm e2e:report`.
3. В рамках текущей задачи допустимо пометить кейс `test.fixme` со ссылкой на созданную задачу. `test.skip` без ссылки — блокер.
4. Кейс правится **только** если доказано, что неверен сам кейс (противоречит спецификации фичи). Тогда правка `.cases.md` и спека идёт одним коммитом, а в отчёте — отдельная строка «ослаблен/изменён ассерт, причина».
5. Расширение объёма («заодно починил») внутри приёмки запрещено: приёмка должна остаться воспроизводимой оценкой состояния, а не смешиваться с разработкой.

### 6.6 Формат отчёта

Отчёт содержит разделы: **Прогоны** (таблица шаг → команда → результат с цифрами), **Покрытие** (сколько кейсов зелёных из сколько, что не автоматизировано и почему, есть ли пункты спецификации без кейсов), **Интерактивная проверка** (сценарий, состояние консоли, отсутствие запросов браузера к :3101, скриншот при изменении UI), **Контрольный опыт** (что ломали, какие кейсы покраснели, откатили ли), **Блокеры**, **Созданные задачи**, **Пропущено и почему**.

Формулировки «всё работает», «тесты прошли», «проверено» без команды и цифр не допускаются.

**Ни один пункт спецификации обеих фич не остался без кейса** и после сокращения по §5 ревью 1. Строки
«неявное требование» добавлены из архитектурных решений (BFF, httpOnly cookie, изоляция по
пользователю) — без них фича формально соответствует описанию, но небезопасна.

Что изменилось в матрице после правок ревью 1 и почему это допустимо:

- **«Кнопка “Войти”»** держится на `AL-FN-01` (кнопка видна, имя точное) и `AL-FN-02` (клик по ней
  реально логинит). Удалённый `AL-FN-11` («логин по Enter») проверял поведение HTML-формы.
- **«Кнопка выхода из аккаунта»** после удаления `HD-FN-15` держится на `HD-FN-08` — и держится
  целиком: кейс проверяет наличие кнопки с именем «Выйти» (шаг 3), её работу (редирект на
  `/auth/login`), удаление cookie сессии и недоступность `/` после выхода. Плюс `HD-FN-14` проверяет
  доступное имя кнопки по роли. Единственное, что ушло вместе с `HD-FN-15`, — «назад в истории», и это
  не требование спецификации, а поведение кэша App Router (§3.4).
- **«Количество встреч»** сохраняет трёхуровневое покрытие `total` ≠ `items.length`: `HD-UT-03`
  (сервис), `HD-API-05` (контракт), `HD-FN-03` (UI сверяется с API). Именно эту ошибку ловит
  контрольный опыт `T2.10`.
- **«Ошибка при неверных данных»** сохраняет проверку неотличимости сообщений на всех трёх уровнях:
  `AL-UT-02`/`AL-UT-03`, `AL-API-02`/`AL-API-03`, `AL-FN-03`/`AL-FN-04`.
- **`forbidNonWhitelisted`** остаётся проверенным на обоих входах: тело — `AL-API-08` и `HD-API-16`,
  query — `HD-API-10` (шаг 4). Это осознанное решение по `APP_PIPE`, а не дефолт фреймворка.
- **Юниты пункта «подключена к `POST /auth/login`»** перестали быть фиктивными: вместо
  `AL-UT-01…03` со ссылкой на несуществующий `validateUser` там `login`-кейсы и новый блок
  `api-client` (`AL-UT-23…26`), покрывающий склейку URL и нормализацию текста ошибки.
