## 2. Contract

Both routes: class-level `JwtAuthGuard`, no body DTO, no pipe on the params (as `FACT-2062`), so a
request body is ignored. `ownerId` only from `@CurrentUser()` (invariant 5).

| Request                              | Success                                                               | Errors (exact body)                                                                                                                                                                                    |
| ------------------------------------ | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DELETE /meetings/:id`               | `204`, empty; the meeting and **all its files** are gone (FK cascade) | `401` `FACT-2015`; `404` `FACT-2016` for an absent id, a foreign id and an already-deleted id alike                                                                                                    |
| `DELETE /meetings/:id/files/:fileId` | `204`, empty; that one file is gone                                   | `401` `FACT-2015`; `404` `FACT-2016` when the meeting is absent or foreign (checked first); `404` `FACT-2083` when the meeting is owned and the file is absent, already deleted, or on another meeting |

Evaluation order of the file route: guard → ownership (`MeetingAccess`, `FACT-2124`) → file. A
foreign meeting therefore never reveals whether a file id exists on it. Idempotency: not
idempotent in status — a second `DELETE` is `404`, consistent with `ADR-0018` `FACT-3380`/`3392`
(a deleted record is indistinguishable from one that never existed). Ten-file cap: `FACT-2096`
counts the files a meeting holds when the upload arrives, so each delete frees one slot. Too-deep
paths fall to Express's `404` (§1 row 5), as `FACT-2068`.

### 2a. Where things land

- `DeleteMeeting` (`meetings/application/delete-meeting.ts`) → `MeetingRepository.deleteOwned(ownerId, id): Promise<boolean>`
  → `PrismaMeetingRepository`: `deleteMany({ where: { id, ownerId } })`, `count === 1`; `false` → `MeetingNotFoundError`.
- `DeleteMeetingFile` (`meeting-files/application/delete-meeting-file.ts`) → `MeetingAccess.ownsMeeting`
  → `MeetingNotFound`; then `MeetingFileRepository.deleteByIdForMeeting(meetingId, fileId): Promise<boolean>`
  → `deleteMany({ where: { id: fileId, meetingId } })`; `false` → `MeetingFileNotFound`.
- Both handlers `@Delete(...)` + `@HttpCode(HttpStatus.NO_CONTENT)`, return `void`; filters unchanged
  (no new `kind`); use cases wired by `useFactory`; `meetings` does not export `DeleteMeeting`.

## 5. Risks

- Breaking the ownership `where` on a delete destroys data rather than leaking it: a delete case
  must never target `teacher` rows or `mtg-planner-2`, or control (a) wipes the read-only seed.
- An orphaned file is invisible over HTTP (every file route checks the meeting first), so the
  cascade is proven by the FK (§1 rows 1–2) and by control (b), not by reading orphans.
- A cleanup that runs through the route under test fails with it; T2 reports the case's own
  failure first so a broken delete is not misread as a cleanup fault.
- `eraser` appears wherever a case iterates `SEED_USERS`; T2 checks those cases stay green.
