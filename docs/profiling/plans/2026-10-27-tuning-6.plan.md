# Tuning plan, round 6 — `TUNE-S2`, 2026-10-27

**Nine records back this plan, but each tier has very few of its own. The small tier has zero data
points. The medium tier has two (R6, R8, both "trimmed" by the owner's choice). A bug medium tier
has one (R7).** So every effect figure for a tier is **projected**. The only same-kind comparison
across paths is R5 against R6 (review §9, "Comparability"), and even that pair is confounded: R6
reused R5's layout, skill and `ADR-0034`.

**Rests on:** `docs/profiling/reviews/2026-10-27-review.md` (stage `TUNE-S1`, round six). That
review reads R1…R9 under `docs/profiling/runs/` plus the `pnpm verdicts:report` output of
2026-10-27 (V). "§N" below means a section of that review, and "R*n*" uses its abbreviations. No
evidence was gathered for this plan. The documents this plan proposes to change were read to know
their current wording, and nothing was measured from them.

**Direction.** The owner's direction of 2026-10-27: a router skill for `lead` that sizes a task,
feature or bug, and picks a depth of small, medium or large. This plan turns that direction into
proposals. It does not argue for the direction itself. Where the records argue against a part of
it, the proposal says so.

**Order.** The proposals are ordered by the strength of their evidence, not by how they build on
each other. Items 1–2 rest on counted contradictions and `Not found` lines. Item 3 sets the tier
criteria, with an arithmetic argument over the gate yield. Item 4 does the wiring. Item 5 is the
medium tier, which rests on two records. Item 6 is a bug medium tier, which rests on one. Each item
says what it needs from the others, and what happens to it if the others are rejected.

## 3. The router skill: six checkable questions, a tier per answer set

**What changes.** A new skill, `.claude/skills/change-router/SKILL.md` (the name is the owner's
call). It is ours, not an adapter. It owns the **procedure** of choosing a depth, and it deliberately
does **not** list stages. Which stage IDs run in each tier is inventory and goes in
`docs/process.md` (item 4, `ADR-0020`). A stage list in the skill would be the drift class of
`FX-023`/`027`/`031`/`032`.

**Content, to be written by `TUNE-S3`:**

1. **The first question stays in `CLAUDE.md`.** "Has this behaviour already been promised?" picks
   `FEAT` or `FIX`. The router links to it and does not restate it.
2. **The no-behaviour exit.** Documentation, config or a rename with no runtime behaviour gets no
   tier and no stages, only a ledger row. This moves `team-roles`' and `CLAUDE.md`'s existing
   wording here (item 1).
3. **Six criteria**, each answered yes or no **with a citation**: a path, a Routes row, a `FACT-`
   key, an invariant number, an ADR ID.

   | ID  | Question                                                                                                                                                                                       | Source of the wording                              |
   | --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
   | C1  | Does it change an endpoint, a request, response or error body (a Routes row or body in `docs/api-contract.md`), one of the nineteen invariants, or behaviour another feature's cases assert?   | §4 criterion 2, re-worded for "the change"         |
   | C2  | Does it change the schema, an entity or format in `docs/data-model.md`, or the seed?                                                                                                           | new; R1's `G2` shape blocker was data (§3)         |
   | C3  | Does it add or change a protected route or page, the session, a cookie, a token, an auth branch, or touch invariants 16–19?                                                                    | §4 criterion 3, made concrete                      |
   | C4  | Does it touch more than one module of `apps/api`, or both apps?                                                                                                                                | §4 criterion 4                                     |
   | C5  | Does it need a new ADR or supersede one, by `feature-pipeline` §2's list (session scheme, module boundaries, contract format, storage, a refused dependency, a process rule)?                  | new as a sizing criterion; the list already exists |
   | C6  | `FIX` only: was the cause found and proven within about 15 minutes? Answered at `FIX-S4`, not at the start, because it "cannot be judged before the cause is looked for" (`process.md:85-88`). | §4 criterion 1                                     |

4. **The criteria-to-tier table.** This is not a stage table.

   | Tier   | `FEAT` holds when                                                       | `FIX` holds when                                                                               |
   | ------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
   | small  | none of C1–C5                                                           | C1, C3 and C4 do not hold, and C6 is met: today's short path, unchanged                        |
   | medium | any of C1–C4, and not C5 (only if item 5 is approved)                   | only if item 6 is approved: C6 is not met, and C1, C3 and C4 do not hold                       |
   | large  | C5; or any of C1–C4 if item 5 is rejected; or the owner raises the tier | any of C1, C3, C4 holds, or C6 is not met: today's full path (unless item 6 takes the C6 case) |

   For `FIX`, the criteria are exactly §4's four. C2 and C5 are **not** added to the defect
   threshold, so this item changes no defect's path (open question Q2).

5. **The output the `lead` states.** One line, for example:

   ```
   Tier: medium — C1 yes (Routes row DELETE /meetings/:id), C2 yes (seed), C3 yes (PROTECTED_ROUTES), C4 yes, C5 no
   ```

   It goes into the report to the owner before the first dispatch, into every brief, into the
   profiling log and into `FEAT-S7`/`FEAT-S8`'s brief. Item 2 is what makes that line land in a
   record.

6. **Overrides, in the shape of `CH-033` option A.** The owner may raise a tier at any time. A tier
   is lowered only explicitly, and the question put to the owner names every criterion that holds.
   A lower tier is never "recommended" against a higher one. This extends `bugfix-pipeline` §4's
   strictness rule (`:142-147`) to features, because R6 and R8 recorded only "owner's choice" with
   no criteria (§9, first item).
7. **Escalation.** A criterion that appears mid-work raises the tier, and a tier never goes down
   during a run. The `lead` stops dispatching, reports the criterion with its citation, and resumes
   at the earliest stage the new tier adds:
   - small → medium/large: `pnpm change:new <slug>`, and the red test already written stays;
   - medium → large before `FEAT-G3` accepts: `FEAT-S2` and `FEAT-G2` run, with the thin files as
     their input;
   - medium → large after `FEAT-G3`: the same, then `FEAT-S3`/`G3` re-run, and code already written
     is kept and read at `FEAT-G4`.

   The escalation is logged with the stage and the criterion (item 2a). The one recorded instance:
   R6 ordered `ADR-0035` mid-run (R6:6, 44), and `FEAT-S2` ran for the ADR only at 140,079 tokens
   (§2).

**Evidence.**

- All 15 `shape` blockers in the records fell in records that carry a new ADR: R1 2 (`ADR-0017`…
  `0019`), R2 3 (`ADR-0026`), R5 1 (`ADR-0034`), R9 9 (`ADR-0036`, `0037`). Arithmetic over §1's
  ADR column and §3's "Shape blockers by path".
- The two records with no shape blocker (R6, R8) carried an ADR ordered mid-run, or none.
- §6 is the only size rule today, and it is worded for fixes (§7 item 4).
- §6 last line: **Not found:** "router", "tier" or "complexity" in `.claude/**`.

**Effect.** C5 is the only criterion that routes a `FEAT` change to large if item 5 is approved, so
every gate that has ever raised a shape blocker would still run on changes like the ones it raised

**Cost / stops catching.** A misclassified change loses the gates it needed. The risk is
concentrated in C5, which is normally a design output, judged here before design. Escalation is the

document. The argument for paying that on every change: it **replaces** six partial statements

unmeasured (open question Q5).

**Mechanical.** No new role, so `AR-API-07`/`08` are untouched. No new stage ID. The skill count in
`CLAUDE.md` changes (1e). `pnpm check:orientation` is unaffected unless 4d is approved.

**Next run.** The Size block (2a) shows the tier and criteria, and whether the tier held to the

- a `shape` blocker at `FEAT-G3`/`G4` on a medium change;
