## 1. A test-design stage after `FEAT-G3`, as the next free `FEAT-S` number (S9)

**What changes.** One row is added to the `FEAT` table in `docs/process.md` — the only home for the

every test level the change touches, in the homes proposal 5 defines. The header sentence

must contain and what it must not — goes in `feature-pipeline` as a new numbered section between

then `FEAT-S4` onward. **This is not a renumbering**: the number is out of sequence with the

already states the rule; the row order carries the sequence and the ID carries identity.

**Evidence.** The owner's directive, points 1 and 2. The review supports **no** part of it: there is

**Expected effect, projected.** Two effects are claimable and one is not.

- Claimable: `FEAT-S5`'s opaque row is split, so the next round of tuning can see what scenario
  design costs. Projected cost of the stage itself: **150,000–300,000 tokens and 10–25

Nothing stops being caught: no gate is removed or weakened by this item.

**The `CH-004` guard.** Two protections, both mechanical enough to check on the next record: the

**How the next run falsifies it.** The next record carries a row for S9 (the per-stage table gained

**Mechanical consequences.** `AR-API-10` — the new ID must exist in `docs/process.md` **before** any

## 2. A `test-designer` role, with the boundary in the tool list

**Depends on:** proposal 1.

**What changes.** A new `.claude/agents/test-designer.md` **and** a new row in the `team-roles` roles
table — both directions, or `AR-API-07`/`AR-API-08` fail `pnpm verify` (C3). Frontmatter carries all
four required fields; `name` must equal the filename.

Proposed tool list, which is where "does nothing else" is expressed (`ADR-0014`):
**`Read`, `Grep`, `Glob`, `Write`** — no `Edit`, no `Bash`, no `Agent`, no `browser_*`.

- No `Bash`: it cannot run the suite, so it cannot quietly become a tester. Consequence, in the
  shape of `FX-034`: it cannot run `npx prettier --write` on its own output, so **formatting is the
  dispatcher's step**, exactly as for `pipeline-reviewer` and `pipeline-planner`
  (`pipeline-tuning` SKILL.md:111-115). This must be stated in the definition, or a red
  `format:check` is discovered two steps later.
- No `Edit`: it writes scenario files whole and cannot amend a spec or product code in place.
- No `Agent`: the dispatch tree stays two deep (`team-roles` §"Only two roles dispatch").

Model: **`opus`**, by the rule in `team-roles` SKILL.md:45-46 — deciding what is to be checked is a
decision, and a missed scenario costs an iteration. (The alternative, `sonnet`, is defensible because
the stage is bounded by an accepted design; it is named here so the owner can choose. Projected
difference, unmeasured: the record's `opus` rows total 38.2% of the run for 6 of 11 stages.)

**Ownership, which the tool list cannot express (C11).** `team-roles` SKILL.md:68-72 gives
`*.cases.md` to the `tester-*` roles. Proposed resolution, stated as a change rather than a
clarification: **the test designer owns `*.cases.md` — the scenario text — and the `tester-*` roles
own the specs (`**/*.spec.ts`) and the runs.** The sentence in `team-roles` and the matching one in
`feature-pipeline` §6:220-224 both move; the Owns column of four rows changes. The reason the split
survives `ADR-0014`'s intent: the point of that boundary was that no agent grades its own homework,
and separating "what must be true" from "the code that asserts it" keeps that property — it does not
weaken it.

**Evidence.** The owner's directive, point 2. The review supports no part of it; it records that
`tester-functional` appears in no measurement at all, so the role inventory's costs are partly
unmeasured already.

**Expected effect, projected.** One extra dispatch per feature. The record shows 29 dispatches for
the measured cycle; projected 30–31 with proposals 1 and 3 (the S10/S11 split re-uses existing
tester dispatches rather than adding new roles). **Projected.**

**What it costs, and what stops being caught.** Twenty-three roles instead of twenty-two, each of
which is a file someone must keep true. Nothing stops being caught mechanically. What is at risk is
subtler: three tester roles lose the act of writing down what they are about to check, which is
where a tester currently notices that a case is unreachable. Mitigation, and its cost: the tester
that automates a scenario is required to report a scenario it believes wrong rather than silently
rewriting it — which is proposal 9's escalation path, one round earlier.

**How the next run falsifies it.** The next record's S9 row names `test-designer` and **one**
dispatch. Two or more dispatches routinely means the brief is wrong or the stage needs a gate — at
which point proposal 1's tripwire and the open question about a gate (Q2) both fire.

**Mechanical consequences.** `AR-API-07` (frontmatter, name = filename), `AR-API-08` (both
directions). `team-roles`'s "Twenty-two roles" in the description and at line 6 becomes
twenty-three, and `CLAUDE.md`'s agent-team table gains a row (C14) — neither is machine-checked, so
both are easy to forget and neither will fail `verify`.

## 3. Test-first ordering: two new stage numbers (S10, S11), `FEAT-S5` retired in place

**Depends on:** proposals 1 and 2. Also depends on open question **Q1** (what "integration" means
here) before S11 can be written precisely.

**What changes.** In `docs/process.md`'s `FEAT` table:

- **S10 — Red tests (unit and API)**, by `tester-unit` and `tester-api`, placed after S9 and
  **before** `FEAT-S4`. Output: specs for the unit and API scenarios, each failing on current code,
  and a recorded red run in which **each new test fails for the reason it was written for** — not on
  a 404, a typo or an import error.
- `FEAT-S4` — Implementation — keeps its ID, its role and its meaning, and moves to sit after S10.
- **S11 — Integration and end-to-end tests**, by `tester-functional`, `tester-api` and
  `tester-security` as the levels require, placed after `FEAT-S4` and before `FEAT-G4`. Entry
  condition: the unit and API tests of S10 are green.
- **`FEAT-S5` keeps its row and its number, marked retired**, with one line saying its work is now
  S10 and S11. It is not deleted: the existing record cites it and `AR-API-10` would fail (C12).

**Not a reordering of existing IDs.** `docs/process.md:40` says "Stages are never reordered or
skipped" and that sentence stays true of a run; what changes is the inventory, once, and it changes
by adding numbers rather than by moving `FEAT-S4` and `FEAT-S5` past each other. The alternative —
keeping `FEAT-S5` and simply running it before `FEAT-S4` — is rejected here, with the reason
recorded so it is not re-proposed: the single existing record measures `FEAT-S5` as "cases plus a
green run at each level touched" costing 1,146,931 tokens, and silently redefining that ID makes the
second record incomparable with the first, which is the whole purpose of the ID being a join key
(`docs/process.md:9-11`).

**Evidence.** The owner's directive, points 7 and 8. Supporting precedent, not evidence for the
change: `bugfix-pipeline` §5 already requires the red test first in the `FIX` flow (C18), and
`FIX-S5` is a stage ID for exactly that.

**Expected effect, projected.** The measured `FEAT-S4` + `FEAT-S5` pair cost **1,470,977 tokens and
74.8 agent-minutes** (324,046 + 1,146,931; 8.7 + 66.1). Projected after the split: **the same
±15%**, because no work is added — it is reordered and one run boundary is added. The claim worth
testing is different and is about where defects are found: the measured cycle's "Found by" values
were research sweeps (2) and a suite run (1); under test-first ordering a defect found by a red
unit/API test at S10 is a **new** value in that column. Projected: 0–2 per cycle. **All projected.**

**What it costs, and what stops being caught.** Three costs, all real:

1. **A second run boundary.** The record shows 24 of `FEAT-S5`'s 66.1 minutes went to `FX-033`
   across twelve full suite runs, and `e2e/README.md` prices a filtered run at 13.1 s and a full one
   at 27–45 s, with ~12 s of fixed server start per call. The red run at S10 is an extra filtered
   call per new test batch: projected **+12–25 s per batch**, negligible against the stage totals.
2. **Rework risk moves earlier.** A test written against a scenario and a contract, before any code,
   is a test written against a document. The measured cycle's rework was 1,018,067 tokens (29.3%),
   of which 407,507 was caught at `FEAT-G4` and included "a cases doc describing the inverse of its
   own check". Projected: that class of rework moves from `FEAT-G4` to S10/S11 rather than
   disappearing.
3. **What stops being caught:** nothing that a gate caught. But the current order has one property
   test-first loses — a tester writing a case **after** reading the implementation notices the fifth
   copy site, which is what `FEAT-G4` found in the measured cycle ("found a fifth copy site in the
   service that the plan had not named"). That gate still runs after S11, so the catch is preserved;
   it just stops being cheap.

**How the next run falsifies it.** The next record carries S10, `FEAT-S4` and S11 as separate rows.
Three checks: the three together against 1,470,977 (tripwire at **+30%**); at least one row in the
ledger's "Found by" column reading a red test at S10, or the ordering bought nothing measurable in
its first cycle; and the count of `FEAT-G4` blockers (2 in the measured cycle) not rising.

**Mechanical consequences.** `AR-API-10` as in proposal 1. The retired `FEAT-S5` row must remain
literally present in `docs/process.md` (C12). `docs/plans/TEMPLATE.md:101-120` and `feature-pipeline`

## 4. Lift the "no test cases in the plan" ban, and point it at the new stage

**Depends on:** proposal 1.

**What changes.** Two files carry the same ban and both must move, or they contradict each other
(C1):

  homes proposal 5 names; the plan still must not restate them.
- `docs/plans/TEMPLATE.md:7-9` — the same sentence in the template's header comment.

What does **not** change: the 100–150 line budget for the plan, the ban on restating the design, and
the ban on a coverage matrix (`e2e/suite-integrity.api.spec.ts`'s job).

**Evidence.** The owner's directive, points 1 and 2, against `feature-pipeline` §4. The reason the
ban exists is cited in the same section and in `CH-004`: the first two plans reached ~2000 lines and
"three of the nine blockers in the second review and both blockers in the third were bookkeeping
introduced by edits to the document itself". The measured cycle's plan was 149 lines and cost 29.3
agent-minutes and 304,155 tokens (review §2).

**What protects against the `CH-004` failure returning.** The directive does not put scenarios back
in the plan — it puts them in a different document written by a different role. That is the
substantive answer, and it is checkable: the plan's line budget stays at 100–150 and
`FEAT-S3`'s cost in the next record is comparable to 304,155. If scenarios leak into the plan, both
numbers move.

**Expected effect, projected.** None on cost. The effect is the removal of a contradiction that
would otherwise make the new stage unimplementable without an agent disobeying a skill.

**What it costs, and what stops being caught.** The ban currently stops a planner from writing a
case list nobody automates. After the change, that failure mode moves to S9 and is caught by
suite-integrity rules 3 and 5 instead — a designed case ID that never appears in a spec fails
`pnpm verify` unless it carries the `- **Not automated:**` marker
(`e2e/suite-integrity.api.spec.ts:58, 312-351`). That is stronger than the prose ban it replaces.

**How the next run falsifies it.** `FEAT-S3` in the next record stays within roughly ±20% of 304,155
tokens and the plan stays within 100–150 lines. If `FEAT-S3` grows, the ban was doing work the
directive did not account for.

  `e2e/regression/<feature>/<feature>.{unit,api,functional}.cases.md`. Point 4 — "grouped and split
  by feature and module" — is **already satisfied**; the only change is who writes them and when.
  This part costs nothing and needs no new structure.
- **End-to-end journey scenarios get their own area files**, one directory per area, named so the
  pairing rules hold: `e2e/journeys/<area>/<area>.functional.cases.md` with the paired
  `<area>.functional.spec.ts`. These are the files point 3 asks the designer to read and **extend**
  rather than duplicate.
- **Integration scenarios: pending Q1.** No file, no prefix and no naming is proposed here, because
  the repository has no such level (C7) and inventing one inside a tuning plan is exactly the move
  this stage is forbidden to make.
- Each new area prefix is registered in `KNOWN_CASE_PREFIXES`
  (`e2e/suite-integrity.api.spec.ts:43`), or the unregistered-prefix guard goes red — by design.

**Evidence.** The owner's directive, points 3 and 4, against `e2e/suite-integrity.api.spec.ts` rules
2, 3 and 6, and `playwright.config.ts:45-60`.

**Expected effect, projected.** No token effect claimed. The claim is structural: a designer reading
one area file sees every journey through that area, which today requires reading four feature
directories.

**What it costs, and what stops being caught.** A new directory class under `e2e/` and one more
prefix per area. The risk this creates is real and should be named: an `e2e/journeys/` file and a
`e2e/regression/<feature>/` file can describe the same behaviour, which is the `FX-023`/`FX-027`
class. The boundary proposed: **a journey file only holds scenarios that cross two or more
features**; a single-feature scenario stays in its feature directory. That is a review judgement,
not a machine check, and it will need one — see Q3.

**How the next run falsifies it.** `pnpm verify` stays green across the cycle, and the next record's
S9 row names which files it wrote. If a journey file and a feature file both carry the same
behaviour, `FEAT-G4` is where it surfaces, as it did for the cases-doc inversion last cycle.

**Mechanical consequences.** Rules 2 and 3 pair by filename, so `<area>.functional.cases.md` needs
`<area>.functional.spec.ts` in the same directory. The `.functional.` suffix routes the file to the
`web` project (`playwright.config.ts:57`) — a journey spec that drives the API only must be named
`.api.` instead. Nothing is added to `docs/plans/<slug>/`, deliberately: see C13.

## 6. The scenario log, generated rather than written

**Depends on:** proposal 5. Partly on Q1.

**What changes.** A generated index — `e2e/scenarios-index.md` — holding, per level and per module,
the case ID and title of every scenario, produced by `pnpm scenarios:index` from the `.cases.md`
files, plus a meta-test in the `PR-API-` family that regenerates it and fails if the file on disk
differs. It is never hand-edited.

**Evidence.** The owner's directive, point 5. Against it: `docs/process.md:7` names four ledger
entries for one fact kept in two copies (`FX-023`, `FX-027`, `FX-031`, `FX-032`), and `FX-031` is
precisely a hand-maintained list of case IDs that drifted — "the Cases column of
`docs/api-contract.md` cited case IDs that do not exist" (`docs/CHANGELOG.md:102`). A hand-written
scenario log is that defect with a new filename.

**Expected effect, projected.** The designer reads one file instead of walking eleven `.cases.md`
files. Projected saving at the S9 stage: **unmeasurable today**, and I will not invent one — the
review has no figure for how much of any stage is reading rather than producing (its first open
question).

**What it costs, and what stops being caught.** A script, one more case in the suite, one more thing
in `pnpm verify` (which is 47–66 s today, `e2e/README.md:238`), and a generated file in git that
every scenario change touches — a merge-conflict surface on a shared file, the class
`feature-pipeline` §4 already calls out for `e2e/README.md` and the unit cases doc. Nothing stops
being caught.

**The cheaper variant, if the owner prefers it.** Do not build the log. Every `.cases.md` already
opens with a Summary table of `ID | Title | Priority`
(e.g. `e2e/process/process.api.cases.md:28-37`), which is per module and per level and is what point
5 describes. The gap is a single cross-feature entry point, and `e2e/README.md` is already the suite
index. Cost: zero. What is lost: the designer greps instead of reading one page.

**How the next run falsifies it.** The staleness check goes red the first time someone adds a
scenario without regenerating — that is the check working. The falsifiable claim is the opposite
one: if the next two cycles never consult the index (the S9 row's tool calls show what was read), it
is a file maintained for nobody and should be deleted.

## 7. Category tags in the vocabulary that already exists

**Depends on:** nothing. Fully separable.

**What changes.** Point 6's categories are expressed as Playwright tags, which must begin with `@`
(C10b), and reuse the names already in the repository rather than adding synonyms (C10a):

- **Level**: `@unit`, `@api`, `@e2e` — and `@integration` pending Q1. On Playwright specs only.
- **Module/feature**: the existing per-feature tags (`@auth-login`, `@home-dashboard`,
  `@meetings-detail`), one per feature, as today.
- **`[Smoke]` → the existing `@smoke`. `[CriticalPass]` → the existing `@p0`**, which is already
  wired to `pnpm e2e:p0`. Neither is renamed and no second name is introduced.
- **Vitest units get no tags.** Vitest has no tag API; the level and module are already encoded in
  the case ID (`AL-UT-09`), which `pnpm test:auth-login` filters on (`package.json:22-24`). This part
  of point 6 costs nothing because it is already true.
- A meta-test rule that **the level tag matches the filename suffix** (`@api` only in
  `*.api.spec.ts`, `@e2e`/`@integration` only where the level's convention says), so the tag cannot
  drift from the project the file actually runs in.

**Selective running is not built** — the owner's instruction. Every commit still runs the whole
suite.

**Evidence.** The owner's directive, point 6, and the vocabulary read out of `e2e/**` (C10a–C10c).

**Expected effect, projected, and it is small — this is the honest number.** `e2e/README.md:236-246`
measures the full suite at **27–45 s** and a filtered run at **13.1 s**, of which ~12 s is starting
both servers regardless of the filter. So the selective running these tags are for would save at
most **~15–30 s per acceptance run at today's 110 tests** — and `e2e/README.md` draws the opposite
conclusion for acceptance today: one full run beats several filtered ones. The tags' value is
therefore a bet on the suite growing, not a saving now. **Projected.**

**What it costs, and what stops being caught.** A tag line on every describe and on new tests, and
one more meta-test. The real cost is duplication: the level is already carried by the filename
suffix and the module by the directory, so a tag is a second copy of both — mitigated by the
suffix-matching rule above, which is why that rule is part of this proposal and not an optional
extra. Nothing stops being caught.

**How the next run falsifies it.** The suite stays green and the next record shows no new cost at
S10/S11 attributable to tagging. The bet fails if, two cycles from now, no `--grep` by level has
been run: then the tags are bookkeeping and should be removed.

## 8. The plan names the tests this change is expected to break

**Depends on:** nothing. Fully separable. Stronger with proposal 9.

**What changes.** `docs/plans/TEMPLATE.md` gains a short subsection after §4 Tasks: **"Tests this
change is expected to break"** — case IDs, why each goes red, and which task closes the window. Not
a new column in the task table: most rows would read "none" and the table is already five columns
wide. `feature-pipeline` §4 gains one sentence pointing at it.

**Evidence.** C9, verified in both directions. The measured cycle's plan already did this in prose:
"the key-set assertions until `MEETING_KEYS` is five keys (T7) … the four are staged together"
(plan lines 113-116) — and `FEAT-G3` caught two commit-ordering errors of exactly this class
(review §3). What the plan did **not** foresee is `FX-033`: four cases (`HD-API-13`…`16`) that went
red from a cross-file race, costing 24 of `FEAT-S5`'s 66.1 minutes and twelve full suite runs
(review §2, `docs/CHANGELOG.md:100`).

**Expected effect, projected.** The marked-breakage count rises from 1 (the last cycle's
`MEETING_KEYS`) and the unmarked count falls from 4. Projected; and the honest caveat is that
`FX-033` was a **race**, which a planner reading files cannot see — writing the section down does
not by itself predict it.

**What it costs, and what stops being caught.** A section in every plan, which on most changes will
read "none" — the `CH-004` shape in miniature. `PR-API-04` fails a scaffolded file left with the

answer on every change that gets a plan at all, including bugfixes above the threshold. Nothing
stops being caught.

**How the next run falsifies it.** Two counts in the next record's process observations: tests that
went red **as marked**, and tests that went red **unmarked**. Last cycle: 1 and 4. If unmarked stays
at 4, the section is bookkeeping and should be dropped.

**Mechanical consequences.** `PR-API-01` compares only the section 0 labels across templates
(`e2e/process/process.api.cases.md:41-49`), so adding a section after §4 does not touch it.
`pnpm check:orientation` reads section 0 only. `docs/plans/TEMPLATE-BUGFIX.md` carries no equivalent
of §4 and is left alone unless the owner wants the same section there.

## 9. A disputed test is escalated to the owner, never edited

**Depends on:** nothing. Fully separable.

**What changes.** A rule in `team-roles` (the boundaries section) and in `feature-pipeline`: **an
agent does not modify a failing test that the plan did not mark as expected to break.** If it
believes the test rather than the application is wrong, it reports; `lead` files a `BL-` row in
`docs/BACKLOG.md` carrying the case ID, the exact command and verbatim output, why the test is
believed wrong, what would have to change, and the argument that the implementation is right. The
owner decides.

**Deliberately no new artifact class**: `docs/BACKLOG.md` already has the shape (ID, priority, area,
"Conflicts with" mandatory) and is structurally checked by `e2e/ledger/ledger.api.spec.ts` on every
`pnpm verify`. A new "task" document would be a second backlog.

**Point 8's default conclusion is qualified (C17).** "If a planned scenario cannot be reproduced, the
implementation is wrong" holds **after infrastructure causes are ruled out** —
`bugfix-pipeline` §2:67-75 lists them with a ledger entry each: an orphaned server, a hung
`@playwright/test` (`FX-030`), a parallel `pnpm dev`, and a flickering case whose cause was
measurement order (`SEC-API-05`). Without that clause the first flaky run becomes a code change.

**Evidence.** The owner's directive, points 9 and 10, and C9's worked example.

**The worked example, and it is the cost of this item.** `FX-033`: four cases asserted an exact
count delta and broke when a second spec file began mutating the same owner under
`fullyParallel: true`. The agent concluded the **tests** were wrong — correctly; they were rewritten
to title-based assertions and verified over five consecutive full `api` runs
(`docs/CHANGELOG.md:100`). **Under this proposal that fix would not have happened inside the cycle.**
It would have become a `BL-` row for the owner, and `FEAT-S6` — defined as one green `pnpm verify` —
could not have passed until the owner answered. So the cost is stated precisely: **escalation blocks
acceptance.** Projected frequency, from the one record: **one per cycle.**

Two ways to resolve it, and the owner picks one at `TUNE-G1`:

- **(a) The escalation pauses the cycle** and the owner answers before acceptance. Keeps "no done
  without a green `pnpm verify`" (`feature-pipeline` §9) intact. Costs owner latency on roughly one
  occasion per cycle, projected.
- **(b) The cycle closes with the dispute open**, the disputed case marked
  `- **Not automated:** <BL- id>` so suite-integrity rule 5 stays green, and the ledger carries the
  `BL-` row. Keeps the pipeline unblocked; costs a case that stops executing for as long as the
  dispute is open — and the ledger already shows what an unexecuted check is worth (a vacuously
  passing meta-test is one of the recorded defects, `CLAUDE.md`).

I recommend **(a)**, because (b) creates exactly the silent-coverage-loss class this repository has
four entries about. That is a recommendation, not a decision.

**What it costs, and what stops being caught.** It costs the owner's attention, on the record's
evidence about once per cycle. What stops being caught: nothing automatic — but agents lose the
ability to repair a genuinely wrong test quickly, and the measured cycle shows that ability being
used correctly (`FX-033`). This proposal asserts that the risk of an agent bending a test to fit
broken code outweighs the cost of one pause per cycle. **That assertion is the owner's to make; the
record neither supports nor refutes it**, because in its one instance the agent was right.

**How the next run falsifies it.** Count of escalations per cycle in the next record, and how many
the owner resolved as "the test was right". Projected 1 escalation; if the owner finds the agent was
right every time across two cycles, the rule is costing latency for nothing and should be narrowed
to security and contract cases.

## 10. Optional: tolerate the window where a scenario has no spec yet

**Depends on:** proposals 1, 3 and 5. **Approve only if the default below proves intolerable.**

**The problem (C2).** Suite-integrity rule 3 fails a `.cases.md` with no paired spec — only
`*.unit.cases.md` is exempt (`e2e/suite-integrity.api.spec.ts:283-291`). Scenarios written at S9
have no specs until S10 (unit, API) and S11 (integration, e2e). So between S9 and S11 a
`pnpm verify` is **red on rule 3** for the functional and journey cases docs, for reasons unrelated
to the change being correct. This is the same class as the commit-ordering blockers `FEAT-G3` caught
last cycle.

**The default, which needs no change and is what I propose:** accept the window and manage it by
commit ordering, exactly as the last plan did for T1/T3/T7/T8 — the scenario docs and their specs are
staged together, and no `pnpm verify` is treated as acceptance before S11. The pre-commit hook runs
orientation, `lint-staged` and units only (`CLAUDE.md`, "Who runs what"), so nothing forces a red
commit. Cost: a mid-cycle `pnpm verify` is red for a known reason, which must be stated in the
`FEAT-S8` record so it is not read as a defect next round.

**The optional change, if the owner wants the window closed:** amend rule 3 to accept a cases doc
**all** of whose declared IDs carry an explicit pending marker naming the stage that will automate
them — the same single-syntax approach rule 5 uses for `- **Not automated:**`
(`e2e/suite-integrity.api.spec.ts:54-58`), never free prose.

**What stops being caught if the optional change is approved.** Today a cases doc without a spec
fails immediately and unconditionally. After the amendment, an abandoned scenario file survives for
as long as its marker is there — caught by a human reading the marker, not by the suite. The rule
exists because "review does not catch a forgotten `.cases.md`"
(`e2e/suite-integrity.api.spec.ts:5-17`). That is a direct weakening of a check whose stated purpose
is that review fails at this.

**How the next run falsifies it.** The `FEAT-S8` record reports whether a mid-cycle `pnpm verify`
was red on rule 3 and for how long. If it never happened, the optional change is unnecessary; if it
happened and cost more than a few minutes, it pays for itself.

## What I did not propose, and why

- **A gate on the scenarios.** The directive does not ask for one, and each of the four existing
  gates cost 126,135–158,585 tokens and 5.8–8.2 agent-minutes (review §2). A fifth would add a
  projected ~150,000 tokens per cycle. The scenarios are already pressed twice: by the red run at
  S10 (a test that cannot be made to fail for its own reason is a scenario nobody can express) and
  by `FEAT-G4`. See Q2 — if S9 turns out to need two dispatches routinely, that is the evidence for
  a gate, and it will exist next round rather than being assumed now.
- **Renumbering the `FEAT` stages so the table reads in order.** `ADR-0020` forbids it, and a
  superseding ADR to allow it would buy readability at the price of making the one existing record
  uncomparable.
- **Redefining `FEAT-S5` in place** instead of adding S10/S11. Rejected in proposal 3 with the
  reason: it silently changes what a measured number means.
- **A new document class for the escalation task** (point 10). `docs/BACKLOG.md` already has the
  shape and the machine check; a second backlog is the `FX-027` class.
- **Building selective test runs.** Explicitly future work per the owner, and priced in proposal 7:
  worth ~15–30 s per run at today's suite size.
- **An integration level defined here.** Q1. Inventing a test level inside a tuning plan is the
  failure `TUNE-S1`/`TUNE-S2` were split to prevent.
- **jsdom component tests as the integration level.** Already in `docs/BACKLOG.md`'s Rejected
  section: "the UI is covered by functional Playwright tests in a real browser; jsdom would give a
  second, less trustworthy copy of the same checks" (line 75). If Q1 is answered that way, it
  overturns a recorded refusal and needs a reason that was not true then.
- **Mutation testing to prove the new tests fail for the right reason.** Rejected at
  `docs/BACKLOG.md:78` — the control experiments already fill that role at seconds against minutes.
  Point 7's recorded red run is the same mechanism, reversed, and needs no second one.
- **Giving `test-designer` `Bash`.** It would let a read-and-write-docs role run anything
  (`pipeline-tuning` SKILL.md:111-115, `FX-034`). Formatting is the dispatcher's step instead.
- **A hand-written scenario log.** Proposal 6's evidence: `FX-031` is a hand-maintained list of case
  IDs that drifted into citing cases that do not exist.
- **Touching `bugfix-pipeline`.** Points 7 and 9 are already its §5 and §2. The only change the
  directive implies there is proposal 9's escalation rule, which is written in `team-roles` so it
  binds both flows from one place.
- **Adding a required file to the change folder.** C13: it would turn both existing change folders
  red retroactively and force the file on every change above the threshold.

## Open questions the directive does not settle

**Q1 — what does "integration" map to in this repository? (blocks parts of 3, 5, 6, 7)** The levels
that exist are Vitest units, `*.api.spec.ts` (project `api`, no browser), `*.functional.spec.ts`
(project `web`, browser), plus `e2e/security/**`, `e2e/smoke/**` and the meta-tests
(`playwright.config.ts:45-60`). Point 8 distinguishes integration from end-to-end, so one of these
must be true and only the owner can say which: (i) "integration" is the existing API level, and
"end-to-end" is the existing functional level — in which case nothing new is built and the naming
changes only; (ii) integration means the Nest supertest level, which exists as exactly one file kept
for one purpose, "proving `AppModule` boots in a test module", with `CLAUDE.md` saying new HTTP
contract checks go to `e2e/` and **not** there — reopening it reverses that rule; (iii) integration
is a genuinely new level, which needs its own Playwright project or runner, its own ID type code and
a change to `ANY_PREFIX_CASE_ID` (C10c), and is the most expensive of the three. **I did not choose.**

**Q2 — should S9 have a gate?** Not proposed (see above). The evidence that would settle it is the
S9 row in the next record: a stage that needs a second dispatch is a stage whose output is being
corrected by somebody.

**Q3 — what keeps a journey file and a feature file from describing the same behaviour?** Proposal 5
draws the line at "crosses two or more features" and admits it is a review judgement. This
repository has four ledger entries about rules held by review alone.

**Q4 — is the ownership move in proposal 2 acceptable?** It takes `*.cases.md` from three `tester-*`
roles and gives it to one new role. `ADR-0014` is the decision that made tools the boundary; this
does not contradict it, but it does rewrite the "test artifacts belong to testers" sentence that
`ADR-0014` is quoted for. If the owner wants that decision to stay verbatim, the alternative is that
`test-designer` writes scenarios into the change folder and the testers transcribe them — which is
the second-copy disease, and C13's retroactive check failures besides.

**Q5 — where is the red run of point 7 recorded?** No artifact holds it today. The cheapest home is
the tester's hand-back plus one line in the S10 row of the profiling record; a dedicated file is not
proposed. The owner may want it in the cases doc instead, which would make it permanent and
reviewable at the cost of another mandatory field.

**Q6 — how does a tuning plan name a stage that does not exist yet?** Found while writing this file
(C5): `AR-API-10` fails any `docs/profiling/**` file citing an undefined stage ID, so a `TUNE-S2`
plan that proposes a new stage cannot write its ID. The workaround used here — prefix-less numbers —
works and costs nothing, but it is undocumented. If the owner wants it fixed, the options are a
sentence in `pipeline-tuning` describing the convention (cheap, no check weakened) or an exemption
for `docs/profiling/plans/**` in `AR-API-10` (which would stop catching a typo'd stage ID in a plan
— the thing the check exists for). I propose the sentence, not the exemption, and have not made it a
numbered item because it is one line.
