## 2. `FIX-S2` and `FIX-S5` are split: the scenario text to `test-designer`, the spec and the run to the `tester-*`

**Depends on:** nothing mechanically. It decides a question proposal 4 inherits.

**What changes.** Two Role cells in `docs/process.md`'s `FIX` table, plus one clause in `team-roles`.

- `FIX-S2` (Reproduction) — the output is "a command that goes red **now**", not a case in the suite.
  Role stays with the `tester-*` for that level; the Output cell is left alone. **No change needed
  here**, and the owner's claim is narrower than it looked: only `FIX-S5` produces "a case in the
  suite".
- `FIX-S5` (Red test) — Role becomes `test-designer` for the case text, then the `tester-*` for that
  level for the spec and the run. Output splits the same way: a scenario row in the paired
  `.cases.md`, then a spec that is red on current code.
- `team-roles`, the boundaries section, gains one clause: the `*.cases.md` ownership rule governs
  **team dispatches**; below the `bugfix-pipeline` §4 threshold there is no team (`team-roles:113-118`
  already says so), and the fixer writes the case row with the spec.

**The evidence.** D4 and the D2 correction, both verified: `docs/process.md:59,62` against
`team-roles:30,68-77` and `feature-pipeline` §6:257-262. `CH-021`'s entry states the move explicitly
— `test-designer` "takes `*.cases.md` off the three `tester-*` roles" (`docs/CHANGELOG.md:70`).

**The alternative the owner may prefer, stated because it is defensible.** Make the defect flow an
**exception**: the tester writes both the case row and the spec, because a defect's scenario is not
designed — it is dictated by the promise the code broke, which is already written down in a contract,
an invariant or an existing case, and again in the reproduction at `FIX-S2`. That saves one dispatch
per above-threshold defect: **projected 90,000-150,000 tokens and 5-8 agent-minutes**, bracketed by
the cheapest single-dispatch row in the record (`FEAT-S7`: 89,467 tokens, 5.6 min, 25 calls).
**Projected.** Its cost is that it reverses a sentence `CH-021` wrote one round ago with the defect
flow explicitly in view (`team-roles:74-77`), and reversing a decision that recent without new
evidence is how a process starts oscillating. **I recommend the split, not the exception** — but the
exception is the cheaper of the two and the owner is choosing between consistency and a dispatch.

**What it costs, and what stops being caught.** The split costs one `test-designer` dispatch on every
above-threshold defect — projected 90,000-150,000 tokens, as above, **projected**. What stops being
caught if the exception is chosen instead: nothing mechanical. What is at risk is the property
`ADR-0014` and `CH-021` both name — no agent grades its own homework. Note that under the exception
the property is only half lost: the author of the check is still not the author of the fix, which is
the separation `bugfix-pipeline` §5 has always required ("written **first**, by a tester rather than
by whoever will fix it").

**How the next run shows whether it worked.** The first `FIX` record's `FIX-S5` row names one or two
roles and one or two dispatches. If it names `test-designer` and the row's blocker count is zero, the
split cost a dispatch and bought nothing measurable in its first cycle — one cycle does not settle
it, and the record is where the second data point will come from.

**Mechanical consequences.** None fail `verify`. `team-roles`' roles table is unchanged (no role is
added or removed), so `AR-API-07`/`AR-API-08` are untouched. The clause lands in the existing
boundaries section of `team-roles`, not a new one.

## 3. The disputed-test rule is reconciled with `bugfix-pipeline` §6, and the bugfix plan gains a place to mark expected breakage

**Depends on:** nothing. The two halves are **coupled on purpose** — see the justification below.

**What changes.** Two edits that only work together.

- `bugfix-pipeline` §6, third bullet, currently reads: "If the correct behaviour contradicts an
  existing case, **the case is right** until proven otherwise. Once proven, the case and its
  `.cases.md` are edited in one commit and the report gains a line saying 'assertion changed, and
  why'". Since `CH-021` that is false twice over: `.cases.md` is no longer the editing agent's to
  touch (`team-roles:68-77`), and a failing test the plan did not mark as expected to break is
  escalated to the owner and **never edited** by the agent that finds it (`team-roles:78-85`;
  `docs/CHANGELOG.md:70`, "escalation **blocks acceptance**"). The bullet is rewritten to route
  through the escalation path: the agent reports, `lead` files a `BL-` row, the owner decides, and
  the edit — if approved — is made by the role that owns the file.
- `docs/plans/TEMPLATE-BUGFIX.md` gains the analogue of `TEMPLATE.md`'s §4a: a short subsection
  listing **the cases this fix is expected to break**, with the case ID, why it goes red, and which
  task closes the window. It sits with §5 "Fix plan", where the task table already is.

**Why the coupling is real and not a bundle.** The escalation rule is defined relative to "a failing
test **the plan did not mark** as expected to break". `TEMPLATE-BUGFIX.md` has no place to mark one —
its seven sections are reproduction, cause, impact, why-not-caught, fix plan, verification, risks.
So in the defect flow, today, **no** failing test can ever be marked, which means the escalation
rule fires on every one of them and blocks acceptance until the owner answers. Approving the first
half alone makes that worse, not better; approving the second half alone changes nothing, because
nothing reads the section. They go together or neither does.

**The evidence.** The text of `bugfix-pipeline` §6:131-133 against `team-roles:68-85`, both read
directly. The `FEAT` record supplies the only worked example the repository has: `FX-033`, where an
agent concluded four cases were wrong, was **correct**, and rewrote them inside the cycle
(`docs/CHANGELOG.md:100`; record lines 26, 89-92 — 24 of `FEAT-S5`'s 66.1 agent-minutes across twelve
full suite runs). Under the reconciled rule that repair becomes an escalation.

**Expected effect.** No token claim. The falsifiable claim is a count: the number of cases a defect
fix edits **without** an owner decision falls to zero. Today that number is unbounded and unrecorded.

**What it costs, and what stops being caught.** It costs owner latency, and in the defect flow that
cost is higher than in the feature flow: threshold condition 2 is "the fix changes a contract, an
invariant, or behaviour that another feature's cases rely on", so a defect above the threshold is
**disproportionately likely** to make another feature's case red. Projected frequency: **no figure —
no `FIX` cycle has been measured, and the one `FEAT` instance (`FX-033`) is a different flow.** What
stops being caught: nothing. What is lost is speed — the `FX-033`-shaped repair that took one agent
one stage now takes a round trip through the owner. That is the same trade `CH-021` already accepted
for the feature flow; this item extends it rather than inventing it.

**How the next run shows whether it worked.** Two counts in the first `FIX` record: cases that went
red **as marked** in the bugfix plan, and cases that went red **unmarked** and escalated. If
unmarked-and-escalated is zero and marked is zero too, the template section is bookkeeping and should
be dropped. If escalations exceed one per defect, the rule is costing more latency than the feature
flow's version and should be narrowed to contract and security cases.

**Mechanical consequences.** `PR-API-01` compares only the **section 0** labels across the two
templates (`e2e/process/process.api.cases.md:41-49`), so adding a subsection beside §5 does not trip
it; `pnpm check:orientation` reads section 0 only. The template edit must not renumber
`TEMPLATE-BUGFIX.md`'s existing sections. The `bugfix-pipeline` edit is inside §6 and adds no
section, so F3 is satisfied.

## 4. The defect flow gets its own discovery stages — three new numbers, placed after `FIX-S4`

**Depends on:** nothing mechanically; decides the shape the rest of group B attaches to. Its
falsification depends on proposal 7 — see the last paragraph, which is the honest caveat on this
item.

**What changes.** `docs/process.md`'s `FIX` section stops borrowing. The sentence "The discovery
stages `FEAT-S1`…`FEAT-S3` apply above that skill's §4 threshold and are skipped by design below it"
is replaced by three rows of the flow's own, taking the next free `FIX` numbers in the order
`TUNE-S3` writes them, and placed in the table **after `FIX-S4`**:

| Position       | Stage             | Role                                                 | Output                                                                                                      |
| -------------- | ----------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| after `FIX-S4` | **S8** — Research | `researcher` + the sweeps the defect needs           | `research/**`: steps `FIX-S1`-`FIX-S3` written down with citations; the history sweep is always one of them |
| then           | **S9** — Design   | `designer`, or the planner when the fix has no shape | `design.md`, and any ADR the fix's shape needs                                                              |
| then           | **S10** — Plan    | `planner`                                            | `<slug>.plan.md` from `TEMPLATE-BUGFIX.md`                                                                  |

Then `FIX-S5`, `FIX-S6`, `FIX-S7` as today. **The row order carries the sequence; the numbers are out
of sequence on purpose.** `ADR-0020` forbids renumbering and reuse, `docs/process.md:10-11` states
the rule, and `CH-021` already paid this cost for `FEAT-S9`/`S10`/`S11` sitting between `FEAT-G3` and
`FEAT-S4`.

**Why after `FIX-S4` and not before `FIX-S1`.** The threshold decision is made **at** `FIX-S4`
("Impact … is a plan needed"), and `bugfix-pipeline` §4's first condition is "the cause was not found
in about 15 minutes" — a condition that cannot be evaluated before the cause is looked for. The
defect flow's discovery is therefore genuinely downstream of reproduction and cause, which is the
structural reason it was never a copy of the feature flow's and should not become one.

**What each stage is, and what it prevents on a defect specifically** — the argument the bias rule
demands, per stage:

- **S8, research.** Prevents a fix landing without the promise in writing. `bugfix-pipeline` §1 and
  §"Where the discovery stages fit" already require it — "the `researcher-history` sweep is how 'has
  this been fixed before' gets answered from the record rather than from memory" — and a regression
  that is fixed as if it were new is "preparing a third round" (§1). The sweep set is **chosen by the
  defect**, with history always included, instead of the feature flow's fixed four. This is not a new
  artifact: F1 shows `research/README.md` is already scaffolded and already required filled by
  `PR-API-03`/`PR-API-04` for any above-threshold defect.
- **S9, design.** Prevents the one case `bugfix-pipeline` already names: "It becomes real work only
  when the fix has a shape — a changed contract, a new guard, a moved check — and then it needs its
  ADR like any other decision." The stage **shrinks to one line** when the fix has no shape, which is
  the doctrine `docs/process.md:38-39` already states ("Stages are never reordered or skipped, but
  they shrink with the task"). When it is one line the `planner` writes it at S10 rather than a
  `designer` being dispatched; when the fix has a shape, `designer` is dispatched as in the feature
  flow. **Budget: `design.md` for a defect stays at or under 50 lines unless it carries an ADR** —
  projected from `CH-020`'s 300-line budget for a feature's design, not measured.
- **S10, plan.** Prevents the failure `FEAT-G3` caught twice in the measured cycle — commit-ordering
  errors — which bite a defect harder, because `FIX-S5` puts a red test in the tree before `FIX-S6`
  makes it green. It points at `TEMPLATE-BUGFIX.md` (budget 60-100 lines, already written) rather
  than `TEMPLATE.md` (100-150).

**The evidence.** The owner's directive, point 1. D1, verified. **The record supports none of it** —
it measured a feature.

**Expected effect, projected.** The claim is a **reduction**, and it is the point of the item. Today
an above-threshold defect is defined as borrowing stages measured on a feature at:

| Borrowed today                                                | Tokens            | Agent-time   |
| ------------------------------------------------------------- | ----------------- | ------------ |
| `FEAT-S1` + `FEAT-S2` + `FEAT-S3`                             | **1,035,923**     | **67.0 min** |
| plus `FEAT-G1`…`FEAT-G3` if the gates come with them (see Q1) | 436,515           | 22.3 min     |
| the record's whole discovery half                             | 1,472,438 (42.3%) | 89.3 min     |

Projected for the defect-shaped replacement: **S8 120,000-230,000** (fewer sweeps than `FEAT-S1`'s
303,500 for a researcher plus four), **S9 0-150,000** (0 when it is one line written by the planner;
90,000-150,000 when a `designer` is dispatched, bracketed by the cheapest measured single-dispatch
row, `FEAT-S7` at 89,467), **S10 180,000-300,000** (`FEAT-S3` measured 304,155 against a longer
template). Total **300,000-680,000 tokens**. **All projected, all bracketed from a `FEAT` record, and
a defect is not a feature.**

**What it costs, and what stops being caught.** Three costs, all real:

1. **It writes down a path that today is only implied.** A defect above the threshold currently gets
   whatever discovery the orchestrator reads into one sentence. Naming three stages makes them
   dispatchable — and therefore dispatched. The protection is the threshold, which the owner kept:
   below it there is no folder, no stages and no team, and proposal 5 makes that visible in the same
   table.
2. **The design stage's role is conditional**, which is a path-dependent ownership clause against
   `ADR-0014`'s file-level split (`design.md` belongs to `designer` in `team-roles:26`). The
   alternative — always dispatch `designer` — costs a projected 90,000-150,000 per above-threshold
   defect for a document that `bugfix-pipeline` itself says is "usually short, and often one line".
   The owner should pick; I recommend the conditional role and naming it in `team-roles` rather than
   leaving it to judgement.
3. **Nothing stops being caught by this item.** No gate is removed here — that is proposal 6, and it
   is separate precisely so this one can be approved without it.

**How the next run shows whether it worked.** The first `FIX` record carries rows for the three new
stages. **Tripwire: if the three together exceed 1,035,923 tokens, the self-standing flow is more
expensive than the borrowing it replaced and should be reverted to the single sentence.** Second
tripwire: if S9 is dispatched to `designer` on a defect whose fix had no shape, the shrink rule is
not being applied and the budget line should become a hard entry condition.

**The honest caveat.** Approve this without proposal 7 and **no number will ever tell you whether it
worked**: there is no `FIX` record today, and this item does not create one. That is not a reason to
couple them — 4 is implementable alone — but it is the reason 7 exists.

**Mechanical consequences.** `AR-API-10`: the new IDs must be in `docs/process.md` **before** any
record or plan names them, so `TUNE-S3` edits `docs/process.md` first. The procedure text replaces the
body of `bugfix-pipeline`'s existing unnumbered section "Where the discovery stages fit" — **no

## 6. The defect flow's discovery gets **no** review gates — or exactly one, on the plan

**Depends on:** proposal 4. Meaningless without it.

**What changes.** `docs/process.md`'s `FIX` table gains **no `FIX-G` rows**. The defect flow keeps the
property it has today: zero review gates, four in the feature flow.

**Why this needs the owner's decision rather than mine.** It is genuinely unclear whether today's one
sentence brings the three gates with the three stages. `docs/process.md:53` names **stages**, not
gates; `CLAUDE.md:107-110` says "each stage's artifact is the next stage's context, and each has its
own review gate". Under the first reading this item writes down the status quo and costs nothing.
**Under the second reading it removes three gates**, and the owner is owed the number: on the
measured `FEAT` cycle `FEAT-G1`, `FEAT-G2` and `FEAT-G3` cost **436,515 tokens and 22.3 agent-minutes**
and raised six blockers — two security cases the research sweep never opened (shape-changing), a
seed-mirror guarantee that was vacuous (shape-changing), and two commit-ordering errors (review §2,
§3). That is what would stop being caught on a defect, if the second reading is the true one.

**What the defect flow has instead, and why I judge it sufficient for most defects.** The feature flow
gates documents against other documents. The defect flow has two mechanical checks the feature flow
never had: the red test at `FIX-S5` must fail **on current code** ("a test that is green on broken
code is not a test", `bugfix-pipeline` §5), and the control experiment at `FIX-S7` reverts the fix and
requires the test to go red again. A wrong cause fails both. The measured `FEAT` cycle is itself
evidence that this class of check finds what review does not: of the three defects found in it, the
"would a diff review have found it" column reads **no** three times, and nine control experiments
caught three things "a code review could not have" (record lines 76-85).

**The alternative, if the owner wants one gate.** A plan review. It is the cheapest gate in the
record — `FEAT-G3`, **126,135 tokens and 6.1 agent-minutes** — and it caught exactly the class that
bites a defect: commit ordering, with a red test in the tree before the fix. It would take the next
free `FIX` gate number, sit after S10, and add a projected 126,000-160,000 tokens to **every**
above-threshold defect. **Projected.** I recommend no gate; the owner may reasonably buy that one.

**What it costs, and what stops being caught.** Stated above, both readings. Note the asymmetry: not
adding a gate is reversible in one round if the first `FIX` record shows blockers arriving late;
adding one is paid on every above-threshold defect from the day it ships.

**How the next run shows whether it worked.** The first `FIX` record's rework table. If rework in the
defect flow is caught at `FIX-S7` (acceptance) rather than earlier, and its token share exceeds the
`FEAT` cycle's 29.3%, a gate is being paid for after the fact and the plan review becomes the evidence
for proposal 6's alternative.

## What I did not propose, and why

- **Copying `FEAT-S9` (test design) into the defect flow as a stage.** A defect's scenario is not
  designed: it is the promise the code broke, already written in a contract, an invariant or an
  existing case, and written again as expected-versus-actual at `FIX-S2`
  (`TEMPLATE-BUGFIX.md` §1). A stage to design one scenario is the `CH-004` shape. The **ownership**
  question is separate and is proposal 2.
- **Copying `FEAT-S10`/`FEAT-S11` (red unit and API first, integration and end-to-end after).** The
  defect flow has had test-first since before the feature flow did: `FIX-S5` writes a red test,
  `FIX-S6` fixes. The split into two stages exists in the feature flow because a feature touches
  several levels at once; a defect is one behaviour at one level, and `FIX-S5` already says "the
  `tester-*` for that level".
- **`FEAT-S10`'s stricter red form — red for the reason it was written for, with the red run
  recorded.** The owner asked directly; the answer is that it is **already satisfied, and by
  something stronger**. `bugfix-pipeline` §5 requires red on current code and says "a test that is
  green on broken code is not a test"; §2 rules out the false-red causes by name (an orphaned server,
  a hung `@playwright/test` — `FX-030` — a parallel `pnpm dev`, a measurement-order flake), which is
  precisely "red for its own reason"; `TEMPLATE-BUGFIX.md` §1 already requires the actual output
  **verbatim**; and §7's control experiment — revert the fix, confirm the test goes red again — is
  strictly stronger than recording one red run, because it proves the test tracks **this** fix.
  Adding the feature flow's wording would add a fourth statement of a rule stated three times.
- **Four review gates on the defect flow.** Projected 436,515-595,875 tokens and 22.3-28.1
  agent-minutes per above-threshold defect, from the measured `FEAT` gates. Proposal 6 offers the one
  gate worth debating.
- **A conditional gate that fires only for security or contract defects.** It would create a third
  path; the owner asked for two.
- **Renumbering the `FIX` rows so the table reads in sequence.** `ADR-0020` forbids it, and a
  superseding ADR would buy readability at the price of making records incomparable.
- **A stage table in `bugfix-pipeline`.** `ADR-0020`: `docs/process.md` is the only home.
- **Editing `ADR-0020:41`'s ID range.** It was true when written; `CH-021` already left it stale for
  the feature flow rather than revising an accepted decision.
- **A profiling record below the threshold.** A record for a one-line fix costs more than the fix.
  The consequence — the short path stays permanently unmeasured — is Q2 below, not a hidden cost.
- **A severity scale or a new ledger type for defects.** `bugfix-pipeline`'s own "What this flow
  deliberately lacks" already refuses both.
- **A separate "bugfix-research" role.** The four `researcher-*` sweeps exist and are reusable; a new
  role means an agent file, a roles-table row and `AR-API-07`/`AR-API-08` in both directions, for a
  brief that differs by its subject and not by its tools.
- **Anything in the Rejected section of `docs/BACKLOG.md`.** Checked against the seven rows quoted in
  review §7; no overlap.

scenario row, that is a change to what the stage outputs, not to who performs it, and it is not
