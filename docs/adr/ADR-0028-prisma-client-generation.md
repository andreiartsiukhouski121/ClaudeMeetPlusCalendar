# ADR-0028 — Prisma is pinned exactly and generated with prisma-client-js into node_modules

- **Status:** accepted
- **Date:** 2026-10-05
- **Supersedes:** —
- **Superseded by:** —

## Context

> **Rationale — not a fact.** `ADR-0027` decides that persistence is PostgreSQL via Prisma. This
> record decides which Prisma, in which shape — a narrower question with its own shelf life, which is
> why it is not folded into that one: Prisma 8 will force this to be revisited, and revisiting it
> must not mean reopening where the data lives.

- `FACT-3596` `npm install prisma @prisma/client` today installs mismatched majors —
  `prisma@8.0.0-rc.20` and `@prisma/client@7.10.0` — because npm's `latest` dist-tag for `prisma`
  points at a release candidate. — `docs/plans/meeting-files/research/probes.md`
- `FACT-3597` Prisma 7 rejects `url` inside the `datasource` block with `P1012`, and accepts instead
  a `prisma.config.ts` plus a driver adapter passed to `new PrismaClient({ adapter })`. —
  `docs/plans/meeting-files/research/probes.md`
- `FACT-3598` The `prisma-client` generator emits TypeScript source whose internal imports carry a
  `.ts` extension, and a consumer importing that output through an explicit `.ts` specifier fails
  under a tsconfig copied field-for-field from this repository's with
  `TS5097: An import path can only end with a '.ts' extension when 'allowImportingTsExtensions' is enabled`.
  — `docs/plans/meeting-files/research/probes.md`
- `FACT-3599` Whether that generator can be configured to emit or consume a different specifier was
  not tested, and `prisma validate` cannot be used to enumerate its options — it accepts an invented
  generator key without complaint. — `docs/plans/meeting-files/research/probes.md`
- `FACT-3600` The `prisma-client-js` generator exists in `7.10.0`, generates into
  `node_modules/@prisma/client`, typechecks `exit=0` under `packages/tsconfig/base.json` plus
  `packages/tsconfig/nestjs.json`, imports under Node ESM in a `"type": "module"` package, and
  imports under `vitest@4.1.2`. — `docs/plans/meeting-files/research/probes.md`
- `FACT-3601` Whether `prisma-client-js` is deprecated or supported going forward was not
  established; the CLI prints an upgrade banner to `8.0.0-rc.20` on every invocation. —
  `docs/plans/meeting-files/research/probes.md`
- `FACT-3602` `.prettierignore` and the eslint ignore lists carry no entry for a generated _code_
  directory; the only generated artifact either of them names is a markdown file. —
  `.prettierignore`, `eslint.config.mjs`
- `FACT-3603` Only `prisma db push` was exercised; `prisma migrate dev` / `deploy` and shadow
  databases were not, and `db push` no longer accepts `--skip-generate` in Prisma 7. —
  `docs/plans/meeting-files/research/probes.md`

## Decision

- `FACT-3604` `prisma`, `@prisma/client` and `@prisma/adapter-pg` are pinned to the exact version
  `7.10.0` in `apps/api/package.json` — no caret, no range — and `pg`, which the adapter drives, is a
  new runtime dependency covered by `pnpm audit --audit-level high`. — this record, `FACT-3596`
- `FACT-3605` The client is generated by the `prisma-client-js` generator, into its default location
  under `node_modules/@prisma/client`. No generated code enters the repository tree. — this record,
  `FACT-3600`
- `FACT-3606` The schema is `apps/api/prisma/schema.prisma` with a `datasource` block carrying no
  `url`; the connection string is supplied by `apps/api/prisma.config.ts` for the CLI and by a
  `@prisma/adapter-pg` driver adapter for the runtime client. — this record, `FACT-3597`
- `FACT-3607` Schema changes reach a database with `prisma db push`. This record does not adopt
  `prisma migrate` or a migrations directory. — this record, `FACT-3603`
- `FACT-3643` `pnpm db:seed` runs `prisma/seed.ts` under plain `node`, and the seed resolves this
  repository's `.js`-suffixed specifiers to their `.ts` files itself, through a `node:module` resolve
  hook it registers on itself before importing anything. No transpiling tool is added for it. — this
  record, `apps/api/prisma/seed.ts`

Rejected:

- `FACT-3608` The `prisma-client` generator — the one import form that was measured fails here, and
  the option space that governs emitted specifiers is untested, so adopting it would mean building
  on an unknown rather than on a measurement. — `FACT-3598`, `FACT-3599`
- `FACT-3609` Enabling `allowImportingTsExtensions` in `packages/tsconfig` — a repository-wide
  compiler relaxation, inherited by both applications and by the e2e project, to accommodate one
  dependency's generated output. — this record
- `FACT-3610` A caret range on either package — the registry's current tags resolve a naive install
  to two different majors, and a lockfile refresh could do it again without anyone asking. —
  `FACT-3596`
- `FACT-3611` A migrations directory now — there is no deployment and no second environment to
  migrate forward, and the workflow was never exercised. — `FACT-3603`
- `FACT-3644` `tsx`, or any other transpiling runner, for the seed alone — a tool and an audit
  surface for one script, in a change that has already had to override two advisories it did not
  choose. — this record, `docs/CHANGELOG.md`, `FX-029`
- `FACT-3645` Plain `.ts` specifiers in the seed — `TS5097` rejects them under this repository's
  tsconfig, and `prisma/**/*` is type-checked, so the file that dodged the convention would fail the
  check instead. — `FACT-3598`, `FACT-3609`
- `FACT-3646` Running the seed from the compiled build — `nest-cli.json`'s `sourceRoot` is `src`, so
  the seed is outside it; and `db:reset` runs before the e2e server starts, which would put a build
  on the critical path of every Playwright run. — `apps/api/nest-cli.json`

## Consequences

- `FACT-3612` Because nothing generated lands in the tree, no `.prettierignore` entry and no eslint
  ignore entry is needed for it, and `pnpm format:check` is unaffected. — `FACT-3602`
- `FACT-3613` `prisma generate` must run before the API is linted, type-checked, built or executed,
  because the client's types do not exist until it does; it is carried as a prefix on those scripts
  rather than as an install hook, so it depends on no package manager's lifecycle-script policy. —
  this record, `pnpm-workspace.yaml`

> **Rationale — not a fact.** The seed's resolve hook is the same trade `ADR-0009` made when it
> chose forty lines of `node:crypto` over passport and bcrypt, at a twentieth of the size: a small
> amount of our own code instead of a dependency whose cost is permanent and whose advisories are
> not ours to schedule. It is not free either. It is non-obvious machinery to find in a seed script,
> and it has one sharp edge — a static `import` added above the `register()` call is hoisted, runs
> before the hook exists and fails with `ERR_MODULE_NOT_FOUND`, which reads like a missing file
> rather than a broken contract. That edge is why the choice is written down here instead of living
> only in the file. It also has a trigger: the hook is justified while exactly one script needs it.
> A second one makes it shared machinery with no owner, and at that point `tsx` is the right answer
> and this fact is the one to supersede.
>
> **This is a decision with a date on it.** It rests on behaviour measured in
> `7.10.0` on 2026-10-05 and on the absence of a statement about `prisma-client-js`'s future, which
> is not the same as a statement that it has one. The trigger to revisit is Prisma 8 leaving release
> candidate; at that point the right move is probably the modern generator with its specifier options
> actually exercised, which is the work this record declined to do on a guess. Choosing the deprecated
> half of a fork because it is the half that was measured is defensible exactly once, and only while
> the measurement is this fresh.
