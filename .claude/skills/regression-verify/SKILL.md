Приёмка фичи целиком. Отличие от скила `playwright-verify`: тот проверяет **одно изменение**
(MCP-браузер + один спек), этот — **фичу как обещание**: все уровни проверок, соответствие сьюта
конвенции, письменный отчёт. Не подменяй их друг другом: смешивание превратит быструю проверку в
десятиминутный ритуал, и её начнут пропускать.

Спецификация сьюта — `docs/plans/feature-plan-testing.md` (конвенция, кейсы, правила устойчивости),
архитектура и задачи — `docs/plans/feature-plan-implementation.md`.

**Ничего не считается сделанным без фактического прогона.** «Проверено» без команды и без цифр в
отчёте — недопустимая формулировка.

Для фичи размера «страница плюс два эндпоинта» **отдельный агент-приёмщик не нужен**: DoD
исполнителя с контрольными опытами и есть приёмка, а повторный прогон того же самого стоит 20 минут
и не добавляет информации. Отдельного ревьюера имеет смысл звать на код-ревью без прогонов — это
быстро. Порядок работ фичи целиком — в скиле `feature-pipeline`.

## 1. Определи предмет приёмки

`<feature>` — slug фичи: `auth-login` или `home-dashboard`. Он же тег Playwright (`@auth-login`) и
префикс ID юнит-кейсов (`AL-UT-`, `HD-UT-`). Соответствие — в `e2e/README.md`.

Перед прогонами сними осиротевшие серверы от прошлых падений — иначе `reuseExistingServer`
переиспользует процесс без нужных переменных окружения, и результат будет ложным в любую сторону:

```bash
netstat -ano | grep :3100        # взять PID из строки LISTENING
netstat -ano | grep :3101
powershell -NoProfile -Command "Stop-Process -Id <pid>"
```

`Get-Process node | Stop-Process -Force` тоже сработает, но убьёт и рабочие dev-серверы
пользователя — **сначала предупреди**.

## 2. Прогоны — восемь шагов, порядок не переставляется

От дешёвого к дорогому: ранний шаг делает поздний осмысленным.

| #   | Шаг                       | Команда                                    | Что ловит именно здесь                                                                                                                           |
| --- | ------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Конвенция сьюта           | `pnpm e2e e2e/suite-integrity.api.spec.ts` | Спек без парного `.cases.md`; файл без суффикса (молча не запускается); ID кейса, описанный но не автоматизированный; юнит-спек без документации |
| 2   | Линт                      | `pnpm lint`                                | `test.only`, `expect` без `await`, `waitForTimeout`, `test.skip`, `page.pause`, условия в тестах                                                 |
| 3   | Типы                      | `pnpm typecheck`                           | Корень (`e2e/**`) + каждый пакет; в web сначала `next typegen`                                                                                   |
| 4   | Юниты фичи                | `pnpm test:<feature>`                      | Логику в изоляции; падение здесь делает прогон e2e бессмысленным                                                                                 |
| 5   | Смоук                     | `pnpm e2e e2e/smoke`                       | Серверы поднялись, сид на месте — до десятков кейсов                                                                                             |
| 6   | API-тесты фичи            | `pnpm e2e --project=api --grep @<feature>` | Контракт. Браузер не поднимается                                                                                                                 |
| 7   | Функциональные тесты фичи | `pnpm e2e --project=web --grep @<feature>` | UI — после подтверждённого контракта, иначе падение UI не отличить от падения API                                                                |
| 8   | Полный прогон             | `pnpm e2e`                                 | Регресс в соседней фиче и гонки при `fullyParallel` — только он их и ловит                                                                       |

Шаги 1–8 **обязательны**. Пропуск любого — блокер, а не экономия времени. При падении на шаге N
шаги N+1 и далее не запускаются, пока падение не устранено или не оформлено задачей (§5).

### Как прогонять это быстро

**Измерено на этом репозитории** (тёплый `.next`): один `pnpm e2e` — 28 с; семь вызовов с разными
`--grep` — 99 с, то есть каждый дополнительный вызов стоит около 12 с; `pnpm verify` целиком
(lint + typecheck + 41 юнит-тест + 62 e2e) — 1 м 31 с. Экономия от схлопывания вызовов — примерно
минута на проход приёмки, и она заметна потому, что приёмка прогоняется после **каждого** фикса, а
не потому, что один вызов дорог. Три минуты бывают только на действительно холодном `.next`, когда
Turbopack собирает всё заново.

**Поэтому по умолчанию приёмка идёт так:**

```bash
pnpm verify        # lint + typecheck + юниты + ОДИН прогон e2e целиком
```

`pnpm verify` покрывает шаги 2, 3, 4 (в части `pnpm test`) и 5–8 одним подъёмом. Шаг 1
(`suite-integrity`) входит в общий прогон `pnpm e2e`, но его стоит прогнать первым отдельно, когда
менялась структура сьюта: он самый дешёвый и самый информативный при падении.

Разбивка по шагам (`--project=api --grep @<feature>` и прочее) нужна **при падении** — чтобы
локализовать, где именно сломалось, и не гонять браузер, пока не подтверждён контракт. Для зелёного
пути она лишняя.

Что ещё не надо делать: **повторно прогонять полный сьют ради ещё одного зелёного результата.**
Информации это почти не добавляет. Больше даёт точечный контрольный опыт (шаг 10): сломать
поведение, убедиться, что краснеют ожидаемые ID, откатить — секунды и один отфильтрованный прогон.

Двум агентам одновременно — свои порты: `E2E_WEB_PORT=3200 E2E_API_PORT=3201 pnpm e2e`.

Дополнительно к восьми шагам:

- **Шаг 9 — интерактивная проверка**, обязательна для любого UI-изменения. Подними `pnpm dev`,
  дальше по скилу `playwright-verify`: `browser_navigate` на `http://127.0.0.1:3000`,
  `browser_snapshot`, реальный сценарий фичи, `browser_console_messages`,
  `browser_network_requests` (молчаливая 500-ка в fetch выглядит как «всё работает»),
  `browser_take_screenshot` в отчёт. Если инструменты `browser_*` недоступны — скажи это вслух, не
  подменяй «мысленной проверкой».
- **Шаг 10 — контрольный опыт** для каждого нового кейса: сломай проверяемое поведение в
  исходнике, убедись, что прогон **краснеет**, откати. Тест, зелёный при сломанной фиче, хуже
  отсутствия теста. Для этих двух фич контрольные точки заданы планом: `verifyPassword`, всегда
  возвращающий `true` (должны покраснеть `AL-API-02`, `AL-FN-03`), и `countByOwner`, заменённый на
  `items.length` (должны покраснеть `HD-API-05`, `HD-FN-03`).

## 3. Блокеры

Любой из этих пунктов означает «фича не принята». Не «замечание на будущее».

**Прогоны**

- Красный тест на любом из шагов 1–8.
- Заведомо красный тест в коммите. Если проверка невозможна на этом этапе — спек **не создаётся**
  до этапа, где станет зелёным.
- Зелёный прогон, полученный на переиспользованном сервере: убедись, что в логе `webServer` порты
  3100/3101 и что серверы стартовали заново.
- Прогон на портах 3000/3001 вместо 3100/3101; правка `playwright.config.ts` в сторону 3000/3001.

**Конвенция сьюта**

- Спек без парного `.cases.md` или наоборот — кроме файлов из `SELF_EXEMPT`.
- Файл в `e2e/**` без суффикса `.api.spec.ts` / `.functional.spec.ts`: он не попадёт ни в один
  проект и молча не запустится.
- ID кейса описан в `.cases.md`, но отсутствует в спеке и не помечен строкой
  `- **Не автоматизирован:** <причина + ссылка на задачу>` — это единственный распознаваемый
  синтаксис.
- Юнит-спек в `apps/**/src/**`, не упомянутый ни в одном `*.unit.cases.md`; тест, чей заголовок не
  начинается с ID кейса — кроме `SELF_EXEMPT` и `UNIT_SPEC_EXEMPT`.
- Фактическое число тестов не совпало с таблицей ожидаемых чисел (`feature-plan-testing.md` §6.6):
  либо кейс не автоматизирован, либо появился недокументированный тест.

**Качество тестов**

- `test.only`; `test.skip` без комментария с причиной и ссылкой на задачу.
- `waitForTimeout` и любая фиксированная пауза; CSS-локаторы и селекторы по классам (в `apps/web`
  CSS-модули хешируют имена — такой тест умрёт на следующем билде).
- `expect(...)` без `await` для асинхронного матчера. Тест при этом зелёный, не проверив ничего.
- Абсолютные ассерты на счётчики в `@mutating`-кейсах вместо относительных (`N` → `N+1`).
- Мутация данных под read-only пользователями `teacher` / `student`.
- Хардкод логина, пароля или названия встречи вместо `e2e/fixtures/seed.ts`.
- Создаваемая встреча датирована «сегодня» или `Date.now()` вместо 2030 года — ассерт «первая в
  списке» станет зависеть от сида.

**Поведение приложения**

- Обращение браузера к `127.0.0.1:3101` напрямую — нарушение BFF, ловится `HD-FN-11`.
- Ненулевой список `console.error` / `pageerror` вне фильтра HMR-шума из `e2e/fixtures/console.ts`.

**Отчётность**

- Ослабление ассерта под наблюдаемое поведение без явного объяснения в отчёте.
- «Проверено» / «всё работает» / «тесты прошли» без команды и цифр.

## 4. Чек-лист код-ревью

Прогон зелёный — это ещё не приёмка. Прочитай дифф глазами.

Структура:

- новые файлы в `e2e/regression/<feature>/`, имена по шаблону `<feature>.{api,functional}.{cases.md,spec.ts}`;
- `e2e/README.md` дополнен строкой фичи;
- теги `@regression`, `@<feature>`, `@p0` / `@mutating` — через опцию `tag` у `describe`, не текстом
  в заголовке;
- `*.unit.cases.md` ссылается на существующие пути, и наоборот — каждый спек упомянут в документации.

Соответствие кейсов коду:

- **шаги и ожидаемый результат в `.cases.md` совпадают с тем, что реально проверяет спек.**
  Расхождение — блокер: документация начинает лгать, и дальше ей перестают верить;
- негативные кейсы проверяют **и** статус, **и** отсутствие побочного эффекта (данные не
  изменились, токен не выдан, cookie не появилась);
- мутирующие кейсы: выделенный пользователь, `serial`-блок, относительные счётчики, уникальный
  `title`, дата 2030 года;
- ни один кейс не полагается на порядок выполнения других;
- локаторы по роли и лейблу; `getByTestId` — только с обоснованием в комментарии.

Код приложения:

- нет новых проверок HTTP-контракта в `apps/api/test/app.e2e-spec.ts` — по `CLAUDE.md` они идут в
  `e2e/`;
- секреты и хеши не утекают в ответы API и в разметку;
- проверка сессии есть **и** в `proxy.ts`, **и** внутри каждого Server Action: матчер `proxy` не
  покрывает Server Actions надёжно, а сам `proxy` документация Next прямо называет не гарантией
  безопасности.

## 5. Нашли проблему — отдельная задача, план не переписываем

1. **Кейс отражает требование.** Если он красный, по умолчанию неправ код, а не кейс.
2. Дефект оформляется **отдельной задачей**: ID кейса, команда воспроизведения, ожидаемое против
   фактического, ссылка на трейс из `pnpm e2e:report`. Исходные задачи плана не переписываются.
3. Внутри приёмки допустимо пометить кейс `test.fixme` со ссылкой на созданную задачу. `test.skip`
   без ссылки — блокер.
4. Кейс правится **только** если доказано, что неверен он сам (противоречит спецификации фичи).
   Тогда `.cases.md` и спек правятся одним коммитом, а в отчёте появляется отдельная строка
   «изменён ассерт, причина».
5. «Заодно починил» внутри приёмки запрещено. Приёмка — воспроизводимая оценка состояния, а не
   продолжение разработки.
6. После фикса — **весь** пайплайн заново, с шага 1. Частичный перепрогон не доказывает, что фикс
   не сломал соседнее.

## 6. Отчёт

Обязательные разделы:

**Прогоны** — таблица «шаг → команда → результат» с цифрами (`11 passed`, а не «ок»).

**Покрытие** — сколько кейсов зелёных из скольких; что не автоматизировано и почему; есть ли пункты
спецификации фичи без кейсов.

**Интерактивная проверка** — какой сценарий прошли в браузере; состояние консоли; подтверждение,
что запросов браузера к `:3101` нет; скриншот, если менялся UI.

**Контрольный опыт** — что ломали, какие кейсы покраснели, откатили ли.

**Блокеры** — перечень с ID кейса и ссылкой на задачу, либо «нет».

**Созданные задачи** — на каждый найденный дефект.

**Пропущено и почему** — явно, либо «ничего». Пропуск, о котором не сказано, — это не пропуск, а
искажение отчёта.
