Порядок работ для фичи. Скил появился как разбор первой итерации: две простые фичи (страница логина
и дашборд с тремя встречами) заняли около трёх часов, из которых **100 минут ушло на планирование и
вычитку плана и 85 — на код**. Ниже — то, что убирает эти 100 минут, не теряя проверок.

Смежные скилы: `regression-verify` — приёмка фичи; `playwright-verify` — быстрая проверка одного
изменения. Инварианты проекта, которые нельзя выводить заново, — в `CLAUDE.md`.

## 1. Спайк допущений — до плана, не после

**7 минут, выброшенный код, никаких рассуждений.** Один агент (или ты сам) доказывает пробами
пять–семь самых рискованных технических допущений и отдаёт таблицу «допущение → как проверено →
факт».

Почему это первый шаг: в первой итерации ревью плана нашло девять блокеров, и четыре самых дорогих
были поведением библиотек — `@IsOptional()` у двух полей DTO, граница `@Max` против значения в
кейсе, отказ Playwright грузить спек с worker-scoped опцией. Каждое доказывается двадцатью строками
кода за минуты. Вместо этого они были описаны в плане, потом два агента по 25 минут читали план и
собирали те же пробы, потом ещё один 29 минут переписывал план под находки.

**Ревью документа не может заменить запуск кода.** Оно ловит только то, что читатель способен
просимулировать в голове.

Что проверять почти всегда:

- поведение валидации на отсутствующих, пустых и лишних полях;
- код ответа фреймворка по умолчанию (у Nest POST — 201, не 200);
- скоупы и ограничения тестовых фикстур (Playwright отвергает `test.use` для worker-scoped опции
  **в рантайме**, типы это пропускают);
- резолвятся ли специальные импорты в тестовом раннере (`server-only` под Vitest — нет);
- как мержится окружение подпроцессов (`webServer.env` — поверх `process.env`, не вместо).

Пробы складывай в скретчпад, не в репозиторий.

## 2. Компактный план

По шаблону `docs/plans/TEMPLATE.md`, **100–150 строк**, поверх фактов спайка.

Чего в плане быть не должно:

- **перечня тест-кейсов.** Они пишутся один раз, сразу в `e2e/regression/<фича>/*.cases.md`. В
  первой итерации 69 кейсов были описаны в плане, сокращены ревью до 53, а потом всё равно
  переписаны второй раз в файлах сьюта;
- **матрицы покрытия.** Её роль выполняет `e2e/suite-integrity.api.spec.ts`;
- **инвариантов из `CLAUDE.md`.** Их и так читают перед кодом.

Чем длиннее план, тем больше в нём работы, не связанной с фичей: три из девяти блокеров второго
ревью и **оба** блокера третьего были бухгалтерией, внесённой правками самого документа —
разъехавшиеся итоги, переиспользованный номер кейса, сломанная строка таблицы.

## 3. Одно ревью плана

**12 минут. Предмет ревью — три вопроса:**

1. Полнота относительно спецификации: у каждого пункта есть задача и будет тест.
2. Зависимости задач: не требует ли задача фичи 1 артефактов фичи 2 (в первой итерации три
   функциональных кейса логина требовали дашборда — их DoD был недостижим, а исполнитель был бы
   вынужден сломать границу между фичами).
3. Не противоречит ли план фактам спайка.

Поведение библиотек ревью **не проверяет** — это сделал спайк. Второе ревью назначается только
если первое нашло блокер, меняющий архитектуру. Итерация «починил → перепроверил → снова починил»
на бумаге дороже, чем те же правки на живом коде, где их ловит прогон.

## 4. Реализация — параллельно там, где файлы не пересекаются

Бэкенд и веб одной фичи почти всегда независимы по файлам. Два агента:

- каждому — **свой диапазон портов**: `E2E_WEB_PORT=3200 E2E_API_PORT=3201 pnpm e2e` (проверено
  прогоном; переменные читает `playwright.config.ts`, и `API_URL` для web-сервера считается из
  них же);
- при риске пересечения по файлам — **свой git worktree** (см. скил `agent-team`).

В первой итерации я запустил бэкенд и веб последовательно из страха столкновения на портах: 19 + 23
минуты там, где хватило бы 23. Две фичи, трогающие разные модули, тоже могут идти параллельно —
последовательным должен быть только мерж.

Промпт агента не должен пересказывать документы. «Прочитай `CLAUDE.md` и раздел `T1` плана» вместо
списка из восьми документов с указанием разделов: пятеро агентов, читающих одно и то же, — это
минуты в каждом из них.

## 5. Приёмка

По скилу `regression-verify`. Ключевое для скорости:

- **один `pnpm verify`** вместо серии вызовов с разными `--grep`. Измерено: один `pnpm e2e` — 28 с,
  семь вызовов — 99 с, `pnpm verify` целиком — 1 м 31 с. Выигрыш около минуты на проход, и он
  накапливается, потому что приёмка идёт после каждого фикса;
- разбивка по фичам нужна для **локализации падения**, а не для приёмки;
- **повторный полный прогон почти ничего не добавляет.** В первой итерации я прогнал 62 теста
  восемь раз. Информации больше даёт точечный контрольный опыт: сломать поведение, убедиться, что
  краснеют ожидаемые ID, откатить — секунды и один отфильтрованный прогон;
- для фичи размера «страница плюс два эндпоинта» отдельный агент-приёмщик не нужен: DoD
  исполнителя с контрольными опытами и есть приёмка. Отдельного ревьюера имеет смысл звать на
  код-ревью без прогонов — это быстро.

## 6. Что не сокращать

Три вещи стоят дёшево и уже окупились:

- **Контрольные опыты.** Один `sed` плюс отфильтрованный прогон. Именно они вскрыли мета-тест,
  который сканировал не тот каталог, находил ноль файлов и потому зеленел при **любом** нарушении
  конвенции. Ни типы, ни линт, ни ревью такого не видят.
- **Парность `.cases.md` ↔ спек и мета-тест конвенции.** Написан один раз, работает всегда.
- **Фактический прогон перед словом «готово».** Отличает результат от отчёта о результате.

## 7. Бюджет времени

Ориентир для фичи «страница плюс два эндпоинта»:

| Этап                      | Минут   |
| ------------------------- | ------- |
| Спайк                     | 7       |
| План                      | 10      |
| Ревью плана               | 12      |
| Реализация (бэкенд ∥ веб) | 25      |
| Приёмка                   | 10      |
| **Итого**                 | **~65** |

Две фичи с параллельной реализацией и последовательным мержем — около 90 минут, а не три часа.

Если выходит вдвое больше — причина почти всегда в объёме плана или в числе итераций ревью, а не в
сложности кода. Проверь по этому списку, прежде чем искать её в другом месте.

## 8. Отчётность по ходу

Пользователь не видит, что происходит внутри фонового агента, и не может отличить долгую работу от
зацикливания. Поэтому в промежуточных сообщениях называй: сколько агентов запущено, что делает
каждый, сколько этапов осталось. «Работаю» без этого читается как зависание — и справедливо.
