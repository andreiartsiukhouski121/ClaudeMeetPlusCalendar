Use after editing anything under apps/web or apps/api, and when the user asks to "проверь через Playwright", "проверь что работает", "verify the change", "прогони e2e", "напиши e2e тест", or reports that a feature is broken in the browser.

Этот скил — **быстрая проверка одного изменения**. Приёмка фичи целиком (обязательный прогон
юнитов, API- и функциональных тестов, ревью конвенции сьюта, отчёт) — скил `regression-verify`.
Одно другое не заменяет: если смешать, быстрая проверка станет десятиминутным ритуалом и её
начнут пропускать.

Изменение считается сделанным только после зелёного прогона Playwright. Не отчитывайся о готовности
по диффу — дифф не показывает, что страница отрендерилась и что эндпоинт ответил. Проверять нужно
двумя способами: MCP-браузером (увидеть своими глазами сейчас) и spec-файлом (чтобы это же
проверялось всегда потом).

Приложения: `apps/web` — Next.js, `apps/api` — Nest.js. Адреса — именно `127.0.0.1`, не
`localhost` (на Windows тот резолвится в `::1`, куда `next dev` не слушает).

**Порты Playwright — 3100 (web) и 3101 (api), а не обычные 3000/3001.** Playwright поднимает свои
серверы сам, на своих портах. Не переводи прогон на 3000/3001: там может висеть `next start` с
прежней сборкой, которая не подхватывает правки, и прогон даст ложное «зелено» на сломанном коде
(это уже случалось при настройке).

**Но `pnpm dev` и `pnpm e2e` одновременно не работают, несмотря на разные порты.** Next 16
регистрирует dev-сервер по **каталогу проекта**: пока в `apps/web` живёт один `next dev`, второй не
поднимается ни на каком порту, `webServer` Playwright не стартует, и прогон падает с `Exit code: 1`
при нуле запущенных тестов (`Another next dev server is already running`). Проверено опытом.
Поэтому порядок такой: сначала прогон спеков, потом останови прогон и поднимай `pnpm dev` для
интерактивной проверки — или наоборот, но не одновременно.

## 1. Определи, что проверять

| Что менялось                                      | Проверка                                                              |
| ------------------------------------------------- | --------------------------------------------------------------------- |
| `apps/web` — компоненты, страницы, стили, роуты   | MCP-браузер + spec `e2e/regression/<фича>/<фича>.functional.spec.ts`  |
| `apps/api` — контроллеры, сервисы, DTO, эндпоинты | spec `e2e/regression/<фича>/<фича>.api.spec.ts`, фикстура `request`   |
| Оба (фича end-to-end)                             | и то, и другое; сценарий в браузере доводи до реального запроса к API |
| Только конфиги, типы, доки, зависимости           | Playwright можно пропустить — **но скажи об этом вслух**              |

Последняя строка — не лазейка. Пропуск допустим, когда изменение физически не влияет на поведение
в рантайме. Если сомневаешься — проверяй.

## 2. Убедись, что инфраструктура на месте

```bash
ls playwright.config.ts                        # конфиг есть?
pnpm exec playwright --version                 # @playwright/test установлен?
```

Если чего-то нет (свежий клон, снесённые `node_modules`) — восстанови и только потом проверяй:

```bash
pnpm install
pnpm add -D -w @playwright/test                # только в корень, не в apps/*
pnpm exec playwright install chromium          # ставим один браузер
```

Playwright живёт в **корне** монорепозитория, а не в `apps/*`: корень не попадает под globs
`pnpm-workspace.yaml`, поэтому `pnpm -r` его не задевает, и один конфиг обслуживает оба приложения.

## 3. Проверь интерактивно через Playwright MCP

Для любого изменения в UI. Dev-сервер поднимай сам — MCP его не поднимает:

```bash
pnpm dev:web        # :3000, или pnpm dev, если сценарий ходит в API
```

Для MCP-проверки годится обычный dev-сервер на :3000 — здесь ты видишь страницу своими глазами и
сразу заметишь, если она не отражает правку. Но **убедись, что это `next dev`, а не `next start`**:
production-сервер отдаёт старую сборку. Кто держит порт, видно так:

```bash
netstat -ano | grep :3000                                   # взять PID из строки LISTENING
powershell -NoProfile -Command "(Get-CimInstance Win32_Process -Filter 'ProcessId=<pid>').CommandLine"
```

Дальше инструментами `browser_*`:

1. `browser_navigate` на `http://127.0.0.1:3000` + нужный путь
2. `browser_snapshot` — дерево доступности: по нему выбирай локаторы для будущего spec
3. `browser_click` / `browser_type` / `browser_select_option` — пройди ровно тот сценарий,
   который затрагивает изменение, а не абстрактный smoke
4. `browser_console_messages` и `browser_network_requests` — ошибки в консоли и упавшие запросы;
   молчаливая 500-ка в fetch выглядит как «всё работает»
5. `browser_take_screenshot` — приложи к отчёту, если менялся внешний вид

Если MCP-инструменты `browser_*` недоступны, значит сервер не подхватился — см. раздел 7. Не
подменяй этот шаг «мысленной проверкой»: скажи, что интерактивная часть недоступна, и оставь
проверку на spec-файлах.

## 4. Закрепи spec-файлом

На каждое поведенческое изменение — новый или обновлённый спек в `e2e/regression/<фича>/`.

**Суффикс имени файла обязателен и определяет проект Playwright:** `*.api.spec.ts` уходит в проект
`api` (фикстура `request`, `:3101`), `*.functional.spec.ts` — в проект `web` (браузер, `:3100`).
Файл со `.spec.ts`, но без одного из этих суффиксов, не попадёт **ни в один** проект и молча не
запустится — прогон будет зелёным, ничего не проверив. У каждого спека обязан быть парный
`<то же имя>.cases.md` с шагами и ожидаемым результатом; это проверяет
`e2e/suite-integrity.api.spec.ts`. Заголовок теста начинается с ID кейса (`AL-FN-03 — …`), иначе
не работают ни `--grep` по ID, ни проверка парности.

Спек обязателен потому, что одноразовая проверка через MCP не защищает от регресса завтра.

```ts
import { expect, test } from '@playwright/test';

test('пользователь видит результат поиска', async ({ page }) => {
  await page.goto('/search');
  await page.getByRole('textbox', { name: 'Запрос' }).fill('алгебра');
  await page.getByRole('button', { name: 'Найти' }).click();
  await expect(page.getByRole('list', { name: 'Результаты' })).toContainText('алгебра');
});
```

Правила, которые здесь ломаются чаще всего:

- **Локаторы по роли/лейблу**: `getByRole`, `getByLabel`, `getByText`, в крайнем случае
  `getByTestId`. Селекторы по CSS-классам запрещены — в `apps/web` CSS-модули с хешированными
  именами, такой тест умрёт на следующем билде.
- **Никаких `waitForTimeout`.** Web-first assertions (`expect(...).toBeVisible()`) сами ждут до
  таймаута из конфига. Фиксированный сон либо замедляет прогон, либо флакает.
- **Обязательный `await` перед `expect(...)`** для асинхронных матчеров. В этом репо нет
  type-aware линта, поэтому забытый `await` молча проходит и линт, и тест — тест будет зелёным,
  не проверив ничего.
- **`test.only` не коммитить.** Локально удобно, в CI `forbidOnly` уронит прогон.
- Для API — фикстура `request`, не `page`: браузер не поднимается вообще. `baseURL` проекта `api`
  уже указывает на нужный порт, поэтому путь пиши относительным: `request.get('/users')`.

## 5. Прогони и убедись, что зелено

```bash
pnpm e2e                        # оба проекта; сам поднимает next dev и nest start
pnpm e2e --project=web          # только браузерные
pnpm e2e --project=api          # только HTTP
pnpm e2e e2e/regression/auth-login/auth-login.functional.spec.ts   # один файл
pnpm e2e --grep @auth-login     # одна фича целиком
pnpm e2e --grep "AL-FN-03"      # один кейс по ID
pnpm e2e:report                 # HTML-отчёт после падения
```

Скрипты называются `e2e*`, а не `test:e2e`: у `apps/api` есть свой `test:e2e` на Vitest+supertest.
`pnpm test` — это юнит-тесты, он Playwright не запускает.

При падении читай трейс из `pnpm e2e:report` и **чини код**. Ослаблять ассерт под наблюдаемое
поведение можно только если ассерт и правда был неверным — и тогда это надо назвать явно, а не
молча поправить и отчитаться о зелёном прогоне.

Проверь заодно, что тест не проходит всегда: сломай проверяемое поведение в исходнике, убедись,
что прогон краснеет, откати. Тест, который зелёный при сломанной фиче, хуже отсутствия теста.

## 6. Отчитайся конкретно

- что именно проверено — сценарий, а не «всё работает»
- чем — MCP-браузер, spec-файл, или оба
- точная команда и её результат (`3 passed`, а не «тесты прошли»)
- скриншот, если менялся UI
- если проверка пропущена — почему

Не пиши «проверено», если прогона не было.

## 7. Если что-то не заводится

- **`EADDRINUSE` на 3100/3101** — осиротевший `node` от прошлого прогона держит порт. Найди
  виновника, а не глуши всё подряд: `netstat -ano | grep :3100`, затем `Stop-Process -Id <pid>`.
  `Get-Process node | Stop-Process -Force` тоже сработает, но убьёт и рабочие dev-серверы
  пользователя — предупреди, прежде чем так делать.
- **Прогон зелёный, хотя фича очевидно сломана** — почти всегда это переиспользованный чужой
  сервер. Проверь, что тесты шли на 3100/3101, и убедись контрольным опытом: сломай проверяемое
  поведение, прогон должен покраснеть. Если не краснеет — тест смотрит не туда, где твой код.
- **MCP-инструменты `browser_*` не появились** — `.mcp.json` подхватывается только при старте
  Claude Code, нужен перезапуск. Если и после него нет: фолбэк на Windows —
  `"command": "cmd", "args": ["/c", "npx", "-y", "@playwright/mcp@latest", "--browser", "chromium"]`.
- **MCP пишет «browser not found»** — `@playwright/mcp` по умолчанию берёт канал Chrome, а в проекте
  стоит только bundled chromium. Флаг `--browser chromium` в `.mcp.json` обязателен.
- **webServer таймаутит** — первая сборка `next dev` тянет `next/font/google` (Geist) по сети,
  офлайн она не поднимется. Это падение сервера, а не Playwright. Логи видны потому, что в конфиге
  `stdout: 'pipe'`; не меняй на `'ignore'`.
- **Прогон долгий на первом запуске** — холодный Turbopack плюс `tsc` у Nest. Таймауты в конфиге
  (180 с / 120 с) под это и подобраны, снижать их не надо.
