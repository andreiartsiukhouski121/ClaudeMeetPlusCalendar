# Логин: юнит-кейсы (Vitest)

- **Парного спека у этого файла нет** — юнит-спеки живут рядом с кодом, в `apps/**`, а здесь
  собрана карта фичи: какой кейс каким спеком закрыт (тест-план §1.7).
- **Запуск:** `pnpm test:auth-login` (это `pnpm -r test -t "AL-UT-"`), полный прогон — `pnpm test`.
- **Обязательное правило:** заголовок юнит-теста начинается с ID кейса —
  `it('AL-UT-09 — …')`. Без этого фильтр `vitest -t "AL-UT-"` не отберёт фичу, а мета-тест
  `e2e/suite-integrity.api.spec.ts` (правило 7) не сможет проверить, что кейс автоматизирован.
- **Группировка:** каждая группа ниже начинается со строки со **путём спека**; мета-тест сверяет,
  что путь существует и что все перечисленные под ним ID встречаются именно в этом файле.

Итого 27 кейсов, все автоматизированы: 18 в `apps/api` (`01…11`, `13…15`, `17`, `19`, `27`, `28`)
и 9 в `apps/web` (`20…26`, `29`, `30`). Кейсы `29` и `30` заведены задачей на фикс по итогам
приёмки фичи 1 (обрезка пароля), а не исходным планом. Номера `12` (объединён в `AL-UT-09`), `16`
(«токен, подписанный другим секретом» — проверял бы `jsonwebtoken`, а не наш код) и `18`
(«несуществующий email → пустой результат» — вырожденный `Map.get`, покрыт `AL-UT-03`)
**не переиспользуются**.

## `apps/web/src/lib/session.spec.ts`

Спек тестирует `apps/web/src/lib/session-cookie.ts` — чистый модуль без `import 'server-only'`
и без `next/headers`. Сам `session.ts` (`cookies()` из `next/headers`) юнитами не покрывается:
Next алиасит `server-only` на пакет, которого нет в `node_modules`, и Vitest такой импорт не
резолвит. Имя файла спека — по тест-плану §1.1.

Глобалы в `apps/web` не включены, поэтому в спеке стоит `import { describe, expect, it } from 'vitest'`.

- `AL-UT-20` P0 — `buildSessionCookieOptions('development')` даёт `httpOnly: true`, `path: '/'`,
  `sameSite: 'lax'`, `secure: false`. Именно `false`: безусловный `secure: true` сломал бы
  проверку в любом окружении, где loopback не считается trustworthy (риск 1 плана имплементации).
- `AL-UT-21` P0 — `buildSessionCookieOptions('production')` даёт `secure: true`, остальные опции
  те же (сравниваются с development-набором целиком, а не по одному полю).
- `AL-UT-22` P1 — `SESSION_MAX_AGE_SECONDS` равен 3600 и совпадает с `JWT_EXPIRES_IN = '1h'`:
  разъезд этих чисел даёт «сессия жива, а токен просрочен».

## `apps/web/src/lib/api-client.spec.ts`

Сетевых вызовов в спеке нет — `apiFetch` целиком проверяется e2e; юнитами закрыты чистая склейка
URL и нормализация текста ошибки. Правки `process.env.API_URL` откатываются в `finally`: это
переменная процесса, общая для всех тестов файла.

- `AL-UT-23` P0 — `resolveApiUrl` склеивает базу с трейлинг-слэшем и без него в один слэш, без `//`
  (плюс путь без ведущего слэша).
- `AL-UT-24` P1 — `resolveApiUrl` уважает `API_URL` из окружения процесса: ровно этим Playwright
  связывает Next на 3100 с Nest на 3101.
- `AL-UT-25` P1 — при отсутствии `API_URL` база — `http://127.0.0.1:3001` (дефолт §3.6 плана
  имплементации).
- `AL-UT-26` P0 — `ApiError.message` нормализуется из **обеих** форм тела Nest: `message` — строка
  (401) и `message` — массив строк (400 от `ValidationPipe`). Без этого пользователь увидит
  `[object Object]` вместо текста ошибки; тело без `message` даёт сообщение из статуса.

## `apps/api/src/auth/auth.service.spec.ts`

Зависимости в этом спеке передаются моками через конструктор, без `Test.createTestingModule`:
юниту нужны моки, а не контейнер.

- `AL-UT-01` P0 — `login` с верным email и паролем возвращает `{ accessToken, user }`, где `user`
  без `passwordHash` (и в сериализованном ответе нет `scrypt`).
- `AL-UT-02` P0 — `login` с неверным паролем бросает `UnauthorizedException` с сообщением
  «Неверный email или пароль».
- `AL-UT-03` P0 — `login` с неизвестным email бросает **то же** исключение с **тем же** сообщением:
  утечки существования аккаунта нет. Сообщения двух веток сравниваются друг с другом, а не с
  константой по отдельности.
- `AL-UT-04` P0 — `accessToken` получен вызовом сервиса токенов (мок вызван один раз, значение
  из мока), а не собран строкой в сервисе.
- `AL-UT-05` P1 — email нормализуется (`trim` + `toLowerCase`) **до** поиска пользователя: мок
  `findByEmail` получает канонический email.
- `AL-UT-06` P0 — сравнение пароля идёт verify-функцией с парой «пароль, хеш из хранилища»;
  прямого сравнения с plaintext нет. Этим же кейсом покрыта делегация `PasswordService` →
  `common/crypto/password.ts`, поэтому отдельного спека у обёртки нет.
- `AL-UT-07` P1 — payload токена содержит ровно `sub` (id) и `email` и не содержит хеша пароля.
- `AL-UT-08` P2 — при ошибке хранилища исключение прокидывается как есть (500-класс), а не
  превращается в 401: иначе падение хранилища выглядит как неверный пароль.

## `apps/api/src/common/crypto/password.spec.ts`

Спек лежит у реализации, а не у `PasswordService`: сервис — DI-обёртка в одну строку на метод,
его собственный спек тестировал бы обёртку, а не поведение (`auth/password.service.spec.ts`
создавать запрещено планом).

- `AL-UT-09` P0 — `hashPassword(plain)` не равен `plain`, имеет формат `scrypt$<saltHex>$<keyHex>`
  (32 hex-символа соли, 128 — ключа), два вызова с одним паролем дают **разные** строки, но оба
  проходят `verifyPassword`.
- `AL-UT-10` P0 — `verifyPassword(plain, hashPassword(plain))` → `true`.
- `AL-UT-11` P0 — `verifyPassword('other', hash)` → `false`; на пустой строке, строке чужого
  формата и обрезанном хеше — тоже `false`, **без исключения**.

## `apps/api/src/auth/token.service.spec.ts`

`JwtService` инстанцируется руками, со своим секретом: юнит не должен зависеть от конфигурации
`AuthModule`.

- `AL-UT-13` P0 — round-trip: `verify(sign(payload))` возвращает исходные `sub` и `email`.
- `AL-UT-14` P0 — `verify` на токене с испорченной подписью бросает ошибку (`invalid signature`).
- `AL-UT-15` P1 — истёкший токен отвергается (`expiresIn` в прошлом, а не фиктивные таймеры:
  `jsonwebtoken` сверяется с реальным временем).

  даёт `undefined`, а найденный пользователь несёт канонический email из сида.
- `AL-UT-19` P0 — публичный маппинг (`toPublic`) содержит ровно `id`, `email`, `name` и не

## `apps/api/src/auth/jwt-auth.guard.spec.ts`

Guard — ~25 строк **нашего** кода с ролью в безопасности, а его e2e-повторы (заголовок без схемы
`Bearer`, подделанная подпись) удалены планом как вырожденные. Разбор заголовка дешевле всего
проверяется юнитом.

- `AL-UT-27` P0 — при `Authorization: Bearer <валидный токен>` guard возвращает `true` и кладёт
  в `request.user` объект `{ id, email }` из payload; `passwordHash` там отсутствует.
- `AL-UT-28` P0 — при отсутствующем заголовке, заголовке без схемы `Bearer`, пустом токене и
  неразбираемом токене guard бросает `UnauthorizedException('Требуется авторизация')` — одна ветка
  отказа на все случаи, 500 недопустима, `request.user` остаётся пустым.

## `apps/web/src/lib/login-credentials.spec.ts`

Заведён **задачей на фикс** по итогам приёмки фичи 1, а не исходным планом. Приёмка нашла, что
`loginAction` обрезал пробелы не только у email, но и у пароля: пароль с пробелом на краю молча
превращался в другой пароль, и его владелец не входил никогда. NIST SP 800-63B прямо запрещает
изменять и усекать введённый пароль. Разбор `FormData` вынесен в чистую функцию именно затем,
чтобы правило стало проверяемым — Server Action юнитом не покрыть.

- `AL-UT-29` P0 — `readLoginCredentials` обрезает пробелы у `email` и **не** трогает `password`:
  ни `trim`, ни нормализации пробелов внутри.
- `AL-UT-30` P1 — отсутствующие поля дают пустые строки и считаются пустыми; пароль из одних
  пробелов пустым **не** считается — валиден он или нет, решает сервер, а не форма.
