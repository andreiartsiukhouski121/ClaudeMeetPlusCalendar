# Главная: UI `/`

- **Парный спек:** `e2e/regression/home-dashboard/home-dashboard.functional.spec.ts`
- **Проект Playwright:** `web` (Desktop Chrome, `baseURL = http://127.0.0.1:3100`)
- **Теги:** `@regression`, `@home-dashboard`, плюс `@p0` у критичных и `@mutating` у изменяющих данные
- **Запуск:** `pnpm e2e --project=web --grep @home-dashboard`
- **Общие предусловия:**
  - Playwright поднял Next на 3100 и Nest на 3101; Next ходит в Nest по `API_URL`.
  - Сессия берётся фикстурой `authedPage` (`e2e/fixtures/auth.fixture.ts`) — реальный UI-логин
    на `/auth/login`, один раз на воркер, новый контекст на каждый тест. Пользователь задаётся
    тестовой опцией `authUser` (по умолчанию `teacher`).
  - Кейсы без сессии объявляют `test.use({ storageState: undefined })` и берут обычную `page`.
  - Эталонные `total`/`items` берутся через фикстуру `apiRequest` (`e2e/fixtures/api.ts`),
    **не** через `request`: в проекте `web` у неё `baseURL` = `:3100`, то есть запрос ушёл бы
    в Next, а не в Nest. Это не нарушает BFF — запрос идёт из Node-процесса теста.
  - Точные числа проверяются только на `teacher` (5 встреч) и `student` (0). Мутирующие кейсы
    работают под `organizer`, выделенным для проекта `web`; ассерты на счётчик относительные.
  - Локаторы — только по роли, метке и тексту. CSS-селекторы запрещены: классы хешируются.

Итого 13 кейсов: P0 — 8, P1 — 4, P2 — 1. Номер `12` объединён в кейс о порядке и отсечении
(`HD-FN-05`), номера `13` и `15` удалены: первый — арифметическое следствие двух других кейсов,
второй («назад в истории после выхода») проверял бы штатное поведение router-кэша Next.
Освободившиеся номера **не переиспользуются**; кейс об обратном редиректе с логина получил
следующий свободный номер `HD-FN-16`, а не номер удалённого кейса фичи 1.

## Кейсы

### HD-FN-01 — неавторизованный на / уходит на логин

- **Приоритет:** P0
- **Тип:** UI-функциональный
- **Теги:** `@p0`
- **Предусловия:** чистый контекст без cookie сессии (`test.use({ storageState: undefined })`;
  само по себе это no-op — глобального `storageState` в конфиге нет, конструкция объявляет, что
  тест берёт обычную `page`, а не `authedPage`).
- **Шаги:**
  1. Открыть `/`.
- **Ожидаемый результат:**
  - Итоговый URL — `/auth/login`, видна форма логина (поле «Email» и кнопка «Войти»).
  - Данных дашборда на странице нет: ни счётчика встреч, ни email пользователя.
  - Редирект делает `proxy.ts` — это DoD задачи `T2.7`.
- **Имя теста в спеке:** `HD-FN-01 — неавторизованный на / уходит на логин`

### HD-FN-03 — количество встреч совпадает с данными API

- **Приоритет:** P0
- **Тип:** UI-функциональный
- **Теги:** `@p0`
- **Предусловия:** сессия `teacher`; эталонные данные берутся через `apiRequest`.
- **Шаги:**
  1. Через `apiRequest` получить `total` для `teacher`.

  - `total` из API не равен длине `items` — то самое различие, которое проверяет и контракт.
- **Имя теста в спеке:** `HD-FN-03 — количество встреч совпадает с данными API`

### HD-FN-07 — создание встречи обновляет счётчик и список

- **Приоритет:** P0
- **Тип:** UI-функциональный (мутация)
- **Теги:** `@p0`, `@mutating`
- **Предусловия:**
  - Сессия `organizer` (`test.use({ authUser: 'organizer' })`) — песочница мутаций проекта `web`.
  - Кейс живёт в serial-блоке в конце файла.
- **Шаги:**
  1. Открыть `/`.
  2. Считать текущее значение счётчика `N`.
  3. Заполнить «Название» уникальным `E2E встреча <суффикс>`, «Дата и время» — значением
     `FUTURE_STARTS_AT_LOCAL` (`2030-01-01T10:00`), нажать «Создать встречу».
  4. Перезагрузить `/`.
- **Ожидаемый результат:**
  - Счётчик становится `N + 1` — проверка относительная, абсолютных чисел под мутирующим
    пользователем не бывает.
  - В списке появился элемент с этим уникальным названием, и он **первый**: дата 2030 года
    позже любой сид-встречи владельца, сортировка DESC.
  - Список по-прежнему содержит не более 3 элементов.
  - После шага 4 данные те же — изменение сохранилось на сервере, а не только в состоянии
    клиента (это и проверяет `revalidatePath('/')`).
- **Имя теста в спеке:** `HD-FN-07 — создание встречи обновляет счётчик и список`

### HD-FN-08 — выход из аккаунта закрывает доступ

- **Приоритет:** P0
- **Тип:** UI-функциональный (мутация состояния сессии)
- **Теги:** `@p0`, `@mutating`
- **Предусловия:**
  - Сессия `organizer`, тот же serial-блок.
  - Кейс логаутится, поэтому обязан работать в **своём** контексте: фикстура `authedPage`
    создаёт новый контекст из файла `storageState` на каждый тест, и сам файл логаут не меняет.
- **Шаги:**
  1. Открыть `/`.
  2. Убедиться, что видна кнопка выхода.
  3. Нажать её.
  4. Открыть `/` снова.
- **Ожидаемый результат:**
  - На шаге 2 видна кнопка с ролью `button` и именем «Выйти».
  - После шага 3 URL — `/auth/login`, видна форма логина, cookie `ps_session` в контексте
    отсутствует (если реализация оставит её, значение обязано быть строго пустым).
  - После шага 4 снова редирект на `/auth/login`; приветствия с email после выхода нет ни на
    одном шаге.
- **Имя теста в спеке:** `HD-FN-08 — выход из аккаунта закрывает доступ`
